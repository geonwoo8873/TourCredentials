# GitHub 관리[Management]

GitHub 관리자의 궁극적인 목표는 사용자의 모든 프로세스를 원할하게 유지하는 것이며 조직 계층 구조의 다양한 수준 및 각 수준과 관련된 관리 작업에 대해 다룬다.

# 1. 팀 수준의 관리

각 사용자는 팀에 추가할 수 있는 구성원으로써 회사 또는 그룹의 구조를 반영하여 연계 액세스 권한 및 멘션으로 조직에서 팀을 만들 수 있다. 팀은 보다 세부적인 수준에서 리포지토리 권한을 구체화하고 팀 구성원 간의 통신 및 알림을 활성화하는 데 유용한 하위 구조이다. 또한 팀을 `Microsoft Entra ID`와 같은 Idp[ID 공급자] 그룹과 동기화할 수 잇으며 변경 내용을 GitHub에 자동으로 복제가 가능하기 때문에 수동 업데이트와 사용자 지정 스크립트의 의존성이 줄어든다. 하지만 이 기능에 대한 사용 가능 여부는 `GitHub Enterprise Cloud`와 인증된 도메인이 필요하다.

> [!TIP]
> **팀 동기화와 함께 Microsoft Entra ID를 사용하여 새 멤버 온보딩, 권한 부여, 조직에 대한 멤버 액세스 제거와 같은 관리 작업을 관리할 수 있다.**

`팀 유지 관리자` 또는 `리포지토리 관리자` 권한이 있는 구성원은 다음과 같이 수행할 수 있다.

* 새 팀을 만들고 부모 팀을 선택하거나 변경
* 팀을 삭제하거나 이름 변경
* 조직 구성원을 추가하거나 제거 혹은 구성원 자격을 Idp 그룹과 동기화
* 조직 내 팀의 표시 여부 변경
* 검토 할당 라우팅 알고리즘을 활용해 끌어오기 요청에 대한 자동 코드 검토 할당을 관리
* 알림 예약
* 팀 프로필 사진 변경

## 1.2 팀 수준 관리 모범 사례

조직에 팀을 구성하면 유연하게 협업이 이루어질 수 있으며 리포지토리와 사용 권한을 구분하기 쉬워진다. 이는 다음과 같이 GitHub 팀 설정에 대한 사례이다.

* GitHub 조직 내에서 그룹 또는 회사의 계층 구조를 반영하는 중첩된 팀을 생성한다.
* 특정 기술 기반으로 팀을 만들어 PR 검토 프로세스를 간소화 시킬 수 있으며, 개인은 관심사나 기술에 따라 유동적으로 팀에 참가할 수 있다.
* Idp와 GitHub 간의 팀 동기화를 사용하도록 설정하면 조직 소유자와 팀 유지 간리자가 조직 내 팀을 Idp 그룹과 연결할 수 있기 때문에 변경 사항이 GitHub로 자동 복사본이 생성되어 수동 업데이트 및 사용자 지정 스크립트에 대한 필요성이 줄어든다.
* 새 구성원 온보딩, 새로운 권한 부여 혹은 액세스 제거와 같이 관리 작업을 관리할 수 있다.

## 1.3 조직 수준의 관리

GitHub에서 조직은 사용자가 한 번에 여러 프로젝트 전반에 걸쳐 협업할 수 있도록 하는 공유 공간이다. 소유자 및 관리자는 정교한 보안 및 관리 기능을 사용하여 조직의 데이터와 리포지토리에 대한 구성원 액세스를 관리할 수 있으며 `소유자` 권한이 있는 구성원은 다음과 활등을 조직 수준에서 수행할 수 있다.

* 조직에 참가하도록 사용자를 초대하고 조직에서 멤버를 제거
* 사용자를 팀으로 구성하고 조직 구성원에게 팀 유지 관리자 권한을 부여
* 조직 리포지토리에서 외부 협력자를 추가하거나 제거
* 멤버에 대한 권한 수준을 부여하고 지정된 리포지토리에 대한 기본 권한 수준을 설정
* 조직 보안 설정 및 청구를 설정하거나 청구 담당 관리자를 할당
* 사용자 지정 스크립트를 사용하여 리포지토리와 마이그레이션 같은 다양한 유형 및 조직 전체 변경 사항 적용

> [!NOTE]
> **사용자 및 리포지토리에 대해 하나의 조직만 설정하는 것을 권장하며, 회사의 특정 제약 조건에 따라 여러 조직을 만들어야 하는 경우 다음 사항에 유의해야 한다.**

* 조직을 복제하거나 타 조직 간에 구성을 공유할 수 없으며, 조직을 생성할 시점부터 모든 것을 설정해야 하며, 이로 인해 설정에서 오류가 발생할 리스크 증가한다.
* 소프트웨어 공급자의 정책에 따라 여러 조직에 일부 애플리케이션을 설치해야 하는 경우 추가 비용 발생 우려되며 일반적으로 지양하는 부분이다.
* 여러 조직을 관리하면 복잡성과 설정 시간이 더 늘어나게 된다.

### 1.4 엔터프라이즈 수준의 관리

엔터프라이즈 계정에는 GitHub Enterprise Cloud 및 Enterprise Server 인스턴스가 포함되며 소유자가 여러 조직에 대한 정책 및 청구를 중앙에서 관리할 수 있다.

해당 엔터프라이즈 수준에서 소유자 권한이 있는 엔터프라이즈 멤버는 다음과 같이 수행할 수 있다.

* 각 엔터프라이즈 구성원이 Idp의 외부 `ID`를 기존 GitHub 계정에 연결할 수 있도록 해당 엔터프라이즈 계정에 `SAML Single Sign-On`을 사용하도록 설정
* 엔터프라이즈에서 조직을 추가하거나 제거 및 조직에 대해 청구를 설정하거나 청구 관리자 할당
* 모든 조직에 대해 리포지토리, 구성원에 적용되는 관리 정책, 프로젝트 정책, 팀 정책 등 다양한 보안 설정을 지정
* 사용자 지정 스크립트를 사용하여 조직에 대한 다양한 유형의 정보를 추출하여 마이그레이션과 같은 엔터프라이즈 전체 변경 사항 적용
* GitHub Connect를 사용하여 GitHub Enterprise Server와 GitHub.com 통합

# 2. GitHub 액세스 인증

> [!WARNING]
> **GitHub 액세스 키에 대한 내용을 다루지만 기본적으로 사용자는 제 3의 사용자에게 절대적으로 공유나 배포를 해서는 안되며, 그외 배포를 해야 한다면 권한을 최소 범위로 부여해야 한다.**

## 2.1 GitHub 인증 옵션

### 2.1.2 사용자 이름 및 암호

관리자는 사용자가 `기본` HTTP 인증 체계라고도 하는 기본 사용자 이름 및 암호 인증 방법을 계속 사용하도록 허용할 수 있다.

> [!CAUTION]
> **현재 GitHub에서는 Git 작업 또는 API 사용에 대한 암호 인증을 지원하지 않는다**

### 2.1.3 개인용 액세스 토큰

PAT[`개인용 액세스 토큰`]는 GitHub API나 명령줄을 사용하는 경우 GitHub에 대한 인증에 암호를 사용하는 대신 대응이 가능한 액세스 방법이다. 사용자는 설정 옵션을 통해 토큰을 생성하고 리포지토리 또는 조직에 대한 권한을 토큰에 연결하는 방식으로 사용자가 Git 명령줄 도구를 사용하여 GitHub와 상호 작용하는 경우 사용자 이름과 암호를 입력하라는 메시지를 출력받게 되면 토큰 정보를 입력 하면된다.

### 2.1.4 SSH

개인용 액세스 토큰을 사용하는 대신 SSH 키를 사용하여 원격 서버 및 서비스에 연결하고 인증으로 활용가능한 접근 방식이다. 사용자가 각 상호 자굥ㅇ에 대해 사용자 이름 및 개인용 액세스 토큰을 제공할 필요가 없으며 SSH키를 생성한 `ssh-agen`에 추가 후 해당 키를 GitHub 계정에 추가한다. SSH 키를 추가하게 되면 보안 레이어가 확보되며, 사용자는 git의 로컬 복사본을 구성하여 자동으로 암호를 제공하거나 명령줄 도구를 사용하여 상호 작용할 때마다 해당 복사본을 수동으로 제공할 수 있다.

SSH 키를 [SAML](#222-saml-sso) SSO(`Single Sign-On`)를 사용하는 조직에서 소유한 리포지토리와 함께 사용할 수 있다. 조직에서 SSH 인증서를 제공하는 경우 사용자는 해당 인증서를 사용하여 GitHub 계정에 인증서를 추가하지 않고 리포지토리에 액세스할 수도 있다.

### 2.1.5 키 배포

배포 키는 사용자에게 단일 리포지토리에 대한 액세스 권한을 부여하는 GitHub의 다른 유형의 SSH 키이다. GitHub는 개인 사용자 계정 대신 리포지토리에 직접 키의 공개된 부분을 연결하고 키의 프라이빗 부분은 사용자의 서버에 남아 있기때문에, 배포 키는 기본적으로 읽기 전용이지만 리포지토리에 추가할 때 쓰기 권한을 별도로 부여할 수 있다.

포크 설정은 다음과 같이 수행하면 된다.
* 리포지토리의 설정으로 이동
* 사이드바의 보안 카테고리 내에서 키 배포를 선택
* 배포 키 추가 옵션을 찾아 키 생성

## 2.2 GitHub의 추가 보안 옵션

MFA(`다단계 인증`)으로 불리는 2FA(`2단계 인증`)은 사용자의 계정에 추가 보호 계층을 추가한다. 2FA를 사용함으로써 사용자가 사용자 이름 및 암호를 사용하여 로그인한 두 개의 형태 인증을 제공한다.

* GitHub는 다음과 같이 2단계 인증에 대한 옵션을 제공한다.
  * 시간 기반 일회성 코드를 생성하는 인증자 앱
  * FIDO2/WebAuthn을 지원하는 하드웨어 보안 키
  * 암호 없는 피싱 방지 인증을 위한 암호 키
  * SMS 기반 인증 코드
  * 

> [!WARNING]
> **현재 공식적으로 권장하지 않는 SMS 기반 인증 코드 방식은 안전하지 않음으로 간주되어 향후 지원이나 보안상에 문제가 발생할 수 있으니 가급적 사용 지양한다.**

* 2FA 적용에 대한 권장 사항
  * GitHub Team 및 Enterprise Cloud의 조직의 경우 조직 소유자는 구성원, 외부 협력자 및 청구 관리자에게 개인 계정에 대해 2FA 인증 방식을 사용하도록 요구할 수 있다.
  * EMU(Enterprise Managed Users) 및 GHE(GitHub Enterprise Server / GHE.com) 관리자는 엔터프라이즈 관리 계정만 2FA를 요구할 수 있지만 사용자의 개인 GitHub.com 계정에는 2FA를 적용할 수 없다.

### 2.2.2 SAML SSO

Idp(ID 공급자)를 사용하여 사용자의 ID를 중앙에서 관리하는 경우 GitHub에서 조직의 리소스를 보호하도록 SAML SSO를 구성할 수 있다. 조직 및 엔터프라이즈 소유자가 리포지토리, 이슈, 끌어오기 요청 등에 대한 액세스를 제어하고 의도치 않는 상황으로 부터 보호할 수 있기 때문에 리소스에 액세스할 때 GitHub는 Idp를 사용하여 인증하도록 사용자를 리디렉션한다.

* SAML 2.0을 표준으로 구현하는 모든 ID 공급자를 지원하며, 다음과 같이 공급자에 대한 공식 지원을 제공한다.
  * AD FS(Active Directory Federation Services)
  * Microsoft Entra ID
  * Okta
  * Automation
  * PingOne

### 2.2.3 LDAP(Lightweight Directory Access Protocol)

LDAP(`Lightweight Directory Access Protocol`)는 사용자 디렉터리 정보에 액세스하고 관리하는 데 널리 사용되는 프로토콜이다. GitHub Enterprise Server에서 LDAP 통합을 사용하면 기존 회사 디렉터리에 대해 사용자를 인증하고 리포지토리 액세스를 중앙에서 관리할 수 잇다.

* GitHub Enterprise 서버는 다음과 같이 LDAP 서비스와 통합된다.
  * Active Directory
  * Oracle Directory Server ENterprise Edition
  * OpenLDAP

# 3. GitHub 조직 및 권한의 작동 방식

## 3.1 리포지토리 권한 수준

* 특정 사용 권한 수준을 할당하여 각 리포지토리에 대한 액세스를 사용자 지정할 수 있으며, 5가지 표준 리포지토리 수준 권한이 있다.
  * 읽기 [`Read`]
    * 프로젝트를 보거나 논의하려는 비코드 기여자에게 사용하는 것을 권장하며, 이 수준은 리포지토리 내에서 콘텐츠를 보아야 하지만 실제로 기여하거나 변경하지 않는 사용자에게 적합하다.
  * 검토
    * 쓰기 권한은 없지만 문제와 끌어오기 요청을 사전에 관리해야 하는 기여자에게 사용하는 것을 권장하며, 이 권한 수준은 코드를 수정하지 않으면서 문제 및 토론을 추적하는 프로젝트 관리자에게 유용하다.
  * 쓰기 [`Write`]
    * 프로젝트에 지속적인 기여하는 사용자에게 부여하는 것이 좋으며, 대부분의 개발자에게 적용되는 표준 권한이다.
  * 유지 관리
    * 리포지토리를 관리가 필요로 하는 프로젝트 관리자에게 권장된다. 민감하거나 안전하지 않은 작업에 대한 액세스 권한 부여는 하지 않는다.
  * 관리자
    * 보안 관리 또는 리포지토리 삭제와 같은 중요하고 안전하지 않은 작업을 포함한 프로젝트에 대한 모든 권한이 필요한 사용자에게 사용하며 이들은 대부분 리포지토리의 소유자 이거나 관리자에 해당된다.

> [!NOTE]
> **모든 권한에 대한 책임 범위는 명확하더라도 조직 구성원, 외부 협력자, 팀에 조직이 소유한 리포지토리에 대한 다양한 수준의 액세스 권한을 부여하기 때문에 각 권한 수준은 리포지토리 콘텐츠 및 설정에 점진적으로 권한을 부여해야 하며, 프로젝트에 필요 이상으로 권한 부여로 인해 문제 발생을 야기하여 각 사용자에 맞는 권한 부여를 해야한다.**

## 3.2 리포지토리 포크(Fork)

포크는 사용자 고유의 GitHub 계정으로 다른 사용자의 리포지토리에 대한 개인 복사본을 만드는 방법이다. 포크를 통해 원래 프로젝트에 영향을 주지 않고 변경에 대한 범위는 자유로우며 해당 고유한 버전이 표시된다. 이는 오픈 소스에 대한 기여나 변경 내용을 안전하게 실험하기 위한 일반적인 워크플로이다.

`업스트림` 리포지토리라고 하는 원본의 리포지토리에서 변경 내용을 끌어와 포크를 최신 상태로 유지할 수 있다.


### 3.2.2 포크 권한 관리(`관리자`)

조직 소유 리포지토리의 유형에 따라 관리자는 리포지토리를 포크할 수 있는지에 대한 여부를 제어할 수 있다.

* 공용 리포지토리 [`Public Repository`]
  * 포크 항상 허용
* 프라이빗 리포지토리 [`Private Repository`]
* 
  * 포크를 사용하지 않거나 특정 조직 구성원으로만 제한
* 내부 리포지토리
  * 동일한 엔터프라이즈 계정 내에서만 포크 가능

포크 설정에 대한 구성은 다음과 같이 수행하면 된다.

* 조직 리포지토리의 설정 이동
* 사이드바의 Access에서 구성원 권한 선택
* 리포지토리 포크 옵션을 찾아 필요에 따라 업데이트

# 4. 리포지토리 인사이트 확인

GitHub의 리포지토리 인사이트는 프로젝트의 활동, 기여도 및 종속성을 모니터링하고 분석하는 기능을 제공한다. 이러한 인사이트를 활용해 프로젝트 상태를 추적하고, 병목 상태를 식별하며 보안을 보장할 수 있다.

## 4.2 리포지토리 인사이트 확인

* GitHub의 리포지토리로 이동
* 리포지토리 이름 하단에서 인사이트 카테고리 선택
* 인사이트 카테고리에서 다음 섹션을 확인
  * 기여자
    * 각 기여자의 커밋, 추가 및 삭제를 포함하여 시간에 따른 기여 그래프 표시
  * 트래픽
    * 고유한 방문자 및 페이지 보기를 포함하여 리포지토리 트래픽을 모니터링
  * 커밋
    * 시간이 지남에 따른 커밋 활동 분석
  * 코드 빈도
    * 일정 시간 주기 마다 추가 및 삭제된 코드 라인 수를 추적
  * 종속성 그래프
    * 리포지리의 종속성을 확인하고 잠재적인 보안 취약성을 식별

## 4.3 리포지토리 인사이트 사용에 대한 모범 사례

* 기여 모니터링
  * 기여자 섹션을 사용하여 주목받는 리포지토리의 활성 기여자 및 영역을 식별
* 트래픽 추적
  * 트래픽 섹션을 사용하여 사요자의 리포지토리와의 상호 작용하는 방식을 이해하고 참여 추세 식별
* 취약성 해결
  * 정기적으로 종속성 그래프를 검토하여 리포지토리가 안전하게 유지되는지 확인

> **리포지토리 인사이트를 활용하여 데이터 기반 결정을 내려 공동 작업, 보안 및 프로젝트 관리를 개선할 수 있다.**

# 5. 사용자 리포지토리 액세스 권한 부여 받는 범위

## 5.2 리포지토리 사용 권한 목록이 지정된 사용자의 작업

리포지토리에서 사용자의 유효 권한은 다음을 비롯한 다양한 요인의 영향을 받는다.

* 리포지토리 역할
  * 관리자
  * 읽기
  * 쓰기
* 팀 멤버 자격
  * 팀의 상속된 권한
* 조직 구성원 자격
  * 기본 조직 권한
  * SSO 요구 사항

> [!TIP]
> 서로 다른 사용 권한 원본을 결합하면 GitHub는 사용자에게 부여된 가장 높은 수준의 액세스를 적용한다. 만약 사용자가 팀을 통해 `읽기` 권한이 있지만 공동 작업자로 할당된 `쓰기` 권한이 있다면 쓰기 권한이 우선적으로 부여된다.
