# GitHub Innersource Management

오픈 소스 소프트웨어의 장점은 상표 개방성이 높아 누구나 참여할 수 있으므로 활동 지표는 높지만, 재산적 가치를 가지는 소프트웨어는 IP[`지적 재산`]의 프라이버시를 중시하는 폐쇄된 시슽템을 통해 액세스를 제한한다. 독점 소프트웨어에 상당한 투자를 진행한 기업의 책임자 입장에서는 사내 기술이 아니라더라도 다양한 형태와 규모의 회사가 업계 내 경쟁력을 우위를 가지고자 하는 목표를 위해 자체 소프트웨어와 IP등 다양한 형태의 자산을 만들고 유지 관리한다.

그러나 오픈 소스에서 사용되는 패턴의 중요성을 비중이 높고 이와 같은 패턴에서 소스 코드 표시 유형, 프로젝트 버그 인식 및 기능 요청 투명성 등이 있기 때문에, 외부 참여 통합을 간소화하는 끌어오기 요청 모델을 선호한다. 개발 부서에 이러한 이점을 도입하길 원하는 기업의 귀중한 소프트웨어를 오픈을 꺼려하기 때문에 이를 보완하는 제공 기능이라고 생각하면 되며 명칭은 `Innersource`가 필요하다는 것이다.

## Innersource 이점

내부 가시성 지원으로 개발자는 타 기업 프로젝트의 소스 코드에 액세스하여 담당 프로젝트를 진행할 경우 생산성을 향상 시킬수 있는 이점을 가지고 있다. 비슷한 문제를 다른 부서가 어떻게 해결하는지 과정을 참조할 수 있으며, 가용성이 있는 코드와 기타 자산을 찾기도 하기 때문에 이슈, 끌어오기 요청 및 프로젝트 계획에 액세스하면 프로젝트의 진행 속도와 방향을 파악하는 데 유용한 데이터도 얻어 프로젝트의 진행 속도와 방향을 파악하는 데 유용한 데이터를 얻을 수 있다.

> [!TIP]
> **GitHub 토론 및 프로젝트를 활용하여 팀 전체 InnerSource 협업을 추가로 지원하는 것을 권장한다.**

### 리포지토리 표시 유형 및 사용 권한 설정

세 가지 수준의 표시 유형으로 GitHub 리포지토리를 구성할 수 있다. 표시 유형 요구 사항을 충족하지 않는 사용자가 리포지토리에 액세스하려고 하면 "찾을 수 없음 [Not Found]"페이지가 표시되고 수준은 다음과 같다. 공용[Pulic] 리포지토리는 모든 사용자에게 표시되며 실제로 오픈 소스이고 조직 내외부의 사용자에게 액세스 권한을 제공하는 프로젝트에서는 이 표시 유형을 사용한다. 또한 내부 리포지토리는 해당 소유 엔터프라이즈[조직] 멤버에게만 표시된다. 개인[Private] 리포지토리는 소유자와 추가한 모든 팀 또는 개인에게만 표시되며 특정 사용자 및 그룹에게 액세스해야 하는 프로젝트에는 이 유형의 표시를 사용한다.

### README Markdown 추가

추가 정보 파일은 프로젝ㅌ트에 대한 기대치를 전달하고 기여를 관리하는 데 도움이 된다. 추가 정보 파일은 다음을 포함할 수 있다.
* 잠재적 소비자가 필요에 맞는지 파악할 수 있도록 프로젝트의 목적과 비전을 명확히 표현한다.
* 프로젝트를 실제로 보여 주는 스크린샷 또는 코드 샘플과 같은 시각적 보조 기능을 제공한다.
* 검토를 위해 앱의 프로덕션 또는 데모 버전으로 연결되는 링크를 포함한다.
* 필수 조건 및 배포 절차에 관한 기대 수준을 설정한다.
* 종속된 프로젝트에 대한 참조를 포함하고 이러한 참조는 다른 사용자의 작업을 승격하는 긍정적인 방법이다.
* Markdown을 활용하여 독자에게 올바른 형식의 콘텐츠를 안내한다.

REAMD.md 파일을 리포지토리의 루트 디렉ㅌ터리 또는 `.github` 디렉터리 내부에 `docs` 루트에서 배치하는 경우 GitHub는 리포지토리 방문자에게 README를 인식하고 자동으로 표시하는 기능을 제공하여 리포지토리에 둘 이상의 추가 정보 파일이 포함된 경우 표시된 파일은 다음 순서대로 위치에서 선택된다.
* `.github` 디렉터리
* 리포지토리의 최상위 디렉터리
* `docs` 디렉터리

> [!NOTE]
> 프로젝트가 시작되면 전자 메일 및 기타 네트워킹 채널을 사용하여 프로젝트를 홍보하고, 적절한 대상 그룹에 접근하면 프로젝트 참여률을 크게 향상 시킬 수 있다.

### GitHub Project 관리

프로젝트의 관심도가 올라가여 급즈아는 사용자와 참여를 관리하기 위해 많은 작업이 요구될 수 있다. 프로젝트에 따라 프로젝트 참가자의 기대 수준을 관리하는 데에 상당한 작업이 필요할 수 있기 때문에, 이를 사전에 해결하기 위해 GitHub에서는 리포지토리의 루트에 있는 `.github` 루트내 파일을 확인해야 한다. 이 파일을 사용하여 프로젝트의 참여 정책을 설명하고, 정확한 세부 정보는 다를 수 있지만 잠재적 기여자에게 프로젝트가 따르는 규칙을 알려주는 것이 좋다.

`CNTRIBUTING.md`가 존재하는 경우 GitHub에서는 사용자가 이슈 또는 끌어오기 요청을 만들 때 이 파일을 따르도록 관련 링크를 제공한다.

### 이슈 및 끌어오기 요청 템플릿 활용

GitHub에서는 새로운 이슈 및 끌어오기 요청을 위한 시작 템플릿을 지원한다. 이러한 템플릿을 사용하여 새로 만드는 이슈나 끌어오기 요청의 초기 설명을 텍스트를 제공하여 사용자가 이슈를 만드는 프로세스를 시작할 때마다 이 콘텐츠가 표시하여 정해진 양식에 대한 규정을 지키도록 유도하고 필요한 정보는 `CONTRIBUTING.md`에서 참조하는 대신 템플릿 텍스트를 양식처럼 사용하여 이슈를 작성할 수 있다.

### 워크플로 정의

외부 참여를 권장하는 프로젝트의 경우 프로젝트에서 따르는 워크플로를 지정해야 한다. 워크플로에는 버그와 기능에 분기를 어디서 어떻게 사용해야 하는지에 대한 세부 정보가 포함되어야 하며, 끌어오기 요청을 여는 방법과 리포지토리 팀 외부 사용자들이 코드를 푸시하기 전에 알아야 할 기타 세부 정보도 포함해야 한다. 혹여나 아직 염두에 두지 않은 경우는 `GitHub 흐름`을 고려해야 하기 때문에 적극 권장한다.

릴리스 및 배포를 관리하기 위한 전략을 전달해야 하며, 워크플로의 해당 부분은 일상적인 분기 및 병합에 영향을 주므로 참가자에게 전달하는 것이 중요하다.

### 프로그램 프로젝트 성공 예측 측정

모든 팀은 진행 중인 프로그램의 성공을 측정하기 위해 추적할 메트릭의 종류에 대해 생각해야 한다. "출시 시간" 및 "보고된 버그"와 같은 기존 메트릭은 여전히 적용 가능하지만 InnerSource를 통해 얻는 이점을 세부적인 설명이 어려울 수 있다. 대신, 외부 참여가 프로젝트 품질을 어느정도 까지의 개선이 가능하지 혹은 되었는지를 보여주는 메트릭을 추가하는 것이 좋다. 리포지토리에서 버그를 수정하고 기능을 추가하는 끌어오기 요청을 외부 출처를 통해 받고 있거나, 프로젝트 및 미래의 성과와 관련된 논의에 적극 참여하는 참가자가 있는지 확인하여, InnerSource 확장을 장려해 조직의 다른 곳에서 이점을 향상하는 프로그램이 있다.

즉 개인과 팀 참여의 가치와 영향을 측정하는 것과 관련된 메트릭은 현실적으로 까다로우며, 오사용될 경우 기존 프로세스와 문화를 손상시켜 조직과 리더십 팀을 향한 정서 악화를 야기할 수 있기 때문에, InnerSource 채택을 측정하는 방법을 고려하고자 한다면 메트릭에 대한 다음과 같이 지침을 고려 해야한다.

* 측정 결과가 아닌 측정 프로세스
  * 코드 검토 소요 시간
  * 끌어오기 요청 크기
  * 진행 중인 작업
* 절대값이 아닌 대상에 대한 측정
* 개인이 아니라 팀 측정
  * 프로젝트의 고유한 참여자 수
  * 코드를 다시 사용하는 프로젝트 수
  * 팀 간 멘션 수
