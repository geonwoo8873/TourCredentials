# 1. 분기 (Brandhes)

분기는 리포지토리의 다른 사용자에게 영향을 최소한으로 줄여 작업을 개발이 가능한 격리된 작업 영역이다. 기능을 개발하고, 버그를 수정하며 리포지토리의 포함된 영역에서 새 아이디어의 구현을 안전하게 실험할 수 있다. 독립 분기에서 작업하는 개발자는 최신 소프트웨어 개발의 일반적인 개념으로 자체 분기를 가짐으로써 자신의 커밋이 분기에서 작업하는 다른 개발자에게 어떠한 영향을 끼치는지에 대한 리스크를 감안하지 않고 변경을 수행할 수 있다.

## 1.1 분기 병합

각 개발자가 별도의 분기에서 작업하도록 하는 것은 개별 생산성에 긍정적이지만 새로운 과제를 제시하기도 하기 때문에 특정 시점에 도달하면 각 개발자의 분기를 같은 공통 분기로 해야 하기 때문에 프로젝트의 규모가 커지면 여러 병합을 수행해야 하며, 각 병합을 추적하고 검토하는 작업의 중요도가 높아진다. 프로젝트에 대한 여러 변경 내용을 추적해야 하는 경우 끌어오기 요청이 들어오는 위치이다.

# 2. 끌어오기 요청 (Pull Request)

끌어오기 요청은 분기 변경 내용을 문서화 하고 개발자 분기의 변경 내용을 기본 분기에 병합할 준비가 되었다는 것을 팀 동료들에게 알리는 방법 중 하나이다. 이해 관계자는 제시된 변경 사항을 검토하고 논의하여 베이스 분기의 코드 품질을 최고 수준으로 유지할 수 있다.

끌어오기 요청은 두 분기 간의 변경 내용을 비교한다.

* 비교 분기는 개발자 고유의 분기로, 개발자가 수행한 특정 변경 내용을 포함한다.
* 기본 분기라고도 하는 베이스 분기는 변경 내용을 병합해야 하는 분기이다.

## 2.1 끌어오기 요청 생성

1. `GitHub.com`에서 리포지토리의 기본 페이지로 이동
2. 분기(`branches`) 메뉴에서 커밋이 포함된 분기 선택
3. 해당 푸시 완료된 파일 목록 상단의 노란색 배너 색상으로 출력되는 끌어오기 요청 비교 단추를 선택하여 연결된 분기에 대한 끌어오기 요청 생성
4. 기본 분기 드롭다운 메뉴에서 변경 내용 병합할 분기를 선택 후 분기 비교 드롭다운 메뉴를 선택하여 변경한 분기를 선택
5. 끌어오기 요청의 제목 및 설명 입력
6. 검토 준비가 된 끌어오기 요청을 생성하려면 끌어오기 요청 만들기 버튼 선택하고, 초안 끌어오기 요청을 만들려면 드롭다운을 선택하고 초안 끌어오기 요청 만들기를 선택한 다음 초안 끌어오기 요청을 선택

## 2.2 끌어오기 요청 상태

* 초안 끌어오기 요청
  * 끌어오기 요청을 생성할 때 검토 준비가 된 끌어오기 요청 또는 초안 끌어오기 요청을 생성하도록 선택할 수 있다. 초안 상태의 끌어오기 요청은 병합할 수 없으며 코드 소유자는 초안 끌어오기 요청을 검토하도록 자동으로 요청되지 않는다.
* 열린 끌어오기 요청
  * 열기 상태는 끌어오기 요청이 활성 상태이며 기본 분기에 병합되지 않음을 의미한다. 커밋을 수행하고 공동 작업자와 잠재적인 변경 내용을 논의하고 검토할 수 있다.
* 닫힌 끌어오기 요청
  * 끌어오기 쵸엉을 기본 분기(`main`)에 병합하지 않고 닫도록 선택할 수 있다. 이 옵션을 분기에 제안된 변경 내용이 더 이상 필요하지 않거나 다른 분기에서 다른 솔루션을 제안하는 경우에 유용하다.
* 병합된 끌어오기 요청
  * 병합된 끌어오기 요청 상태는 비교 분기의 업데이트 및 커밋이 기본 분기와 결합되었음을 의미하며 리포지토리에 대한 푸시
  * 액세스 권한이 있는 사용자는 누구나 병합을 완료할 수 있다.

## 2.3 끌어오기 요청 병합

1. 리포지토리 이름 하단에 끌어오기 요청 카테고리을 선택한다.
2. 끌어오기 요청 목록에서 병합하려는 끌어오기 요청을 선택한다.
3. 끌어오기 요청의 결과 하단 스크롤하여 리포지토리에 대해 사용하도록 설정된 병합 옵션에 따라 다음을 수행할 수 있다.
   1. 끌어오기 요청 병합 옵션바를 선택하여 모든 커밋을 기본 분기에 병합한다. 병합 끌어오기 요청 옵션이 표시되지 않으면 병합 드롭다운 메뉴
   2. 를 선택하고 병합 커밋 만들기 옵션을 선택 후 병합 커밋 만들기 버튼을 선택한다.
   3. 스쿼시 및 병합을 사용하면 모든 커밋을 가져와 하나로 결합할 수 있으며, 리포지토리 기록을 더 읽기 쉽게 정리할 수 있다.
   4. 재 지정 및 병합 옵션을 사용하면 병합 커밋 없이 커밋을 수행할 수 있으며, 선형 프로젝트 기록이 유지된다.
4. 메시지가 표시되면 커밋 메시지를 입력하거나 기본 메시지를 수락한다.
5. GitHub 계정과 연결된 이메일 주소가 다수 인경우 이메일 주소 드롭다운 메뉴를 선택해 Git 작성자 이메일 주소로 사용할 이메일 주소를 선택한다. 드롭다운 메뉴에는 확인된 전자 메일 주소만 표시되며 전자 메일 주소 개인 정보를 사용하도록 설정한 경우 회신 불가능한 GitHub 전자 메일이 기본 커밋 작성자 전자 메일 주소로 사용한다.
6. 병합 확인, 스쿼시 및 병합 확인 또는 다시 지정 및 병합 확인을 선택한다.
7. 필요에 따라 비교 분기를 삭제하여 리포지토리의 분기 목록을 유지할 수 있다.

# 3. 고급 끌어오기 요청 옵션

> 끌어오기 요청을 만들고 병합하는 것 외에도 팀이 고품질 코드를 유지하는 데 도움이 되는 몇 가지의 고급 옵션을 제공한다.

## 3.1 검토자 요청

특정 공동 작업자에게 끌어오기 요청을 검토하도록 요청할 수 있다. 리포지토리에 대한 쓰기 권한이 있는 협력자만 검토자로 선택할 수 있으며, 병합하기 전에 적절한 사용자가 변경 내용을 검토할 수 있다.

1. 끌어오기 요청을 만들거나 볼 때 오른쪽 사이드바에서 검토자 섹션을 찾는다.
2. 리포지토리에 대한 쓰기 권한이 있는 공동 작업자의 GitHub 사용자 이름을 검색하여 선택한다.
3. 선택한 검토자는 끌어오기 요청을 검토하라는 알림을 받게된다.

## 3.2 필수 검토 및 분기 보호 규칙

일부 리포지토리는 병합하기 전에 특정 조건을 충족하기 위해 끌어오기 요청이 필요한 분기 보호 규칙을 사용한다. 일반적인 요구 사항은 다음과 같다.

* 다른 공동 작업자의 승인 검토가 하나 이상 있어야 한다.
* CI 워크플로와 같은 모든 필수 상태 검사를 전달한다.

끌어오기 요청이 이러한 요구 사항을 충족하지 않으면 모든 조건이 충족될 때까지 단추가 비활성화된다. 병합 섹션의 끌어오기 요청 페이지 하단에 있는 리포지토리에 필요한 규칙을 볼 수 있다. 이러한 규칙은 일반적으로 분기 보호 설정에서 리포지토리 관리자에 의해 구성된다.


## 3.3 상태 검사 및 CI

리포지토리에서 GitHHub Actions 또는 다른 CI 시스템을 사용하는 경우 끌어오기 요청은 변경이 수행되면 자동으로 상태 검사를 실행할 수 있다. 끌어오기 요청은 일반적으로 기본 분기에 병합되기 전에 필요한 모든 상태 검사를 통과해야 하며, 실패한 검사는 끌어오기 요청 페이지에 직접 표시된다.

# 4. 즐겨찾기 사용하여 리포지토리 저장

향후 재 방문 하고자 하는 리포지토리를 찾으면 GitHub에서 표시할 수 있다. 리포지토리를 표시하면 즐격찾기 목록중 개인 목록에 저장된다.

리포지토리 즐겨찾기 지정하고자 한다면 다음같이 수행하면 된다.

1. 리포지토리 페이지로 이동
2. 우측 상단 리포지토리 설명란 위 즐겨찾기 드롭다운 버튼 선택

# 5. 키보드 단축키

GitHub는 작업을 더 빠르게 진행하는 데 있어 효율적인 기능을 제공하는 것이 바로 가기 키를 지원한다.

# 6. 명령 팔레트 사용

명령 팔레트를 사용하면 키보드에서 별도로 액션을 취하지 않고도 페이지로 빠르게 이동하거나, 일반적인 작업을 싱행하고 리포지토리를 검색할 수 있다.
