# 1. GitHub에서 제공하는 사용자 ID 인증 및 권한 부여

기존에 사용자 인증은 사용자 ID와 암호를 사용하여 수행해왔으며, 암호는 인즈의 단일 요소 형식이다. 단일 요소 인증의 근본적인 문제로 로그온 정보를 아는 악의 행위를 하는 사용자를 보다 쉽게 가장할 수 있기 때문에 사용자 계정의 보안 위반을 방지하고자 GitHub에서는 보안 모범 사례를 승격하는 데 사용할 수 있는 인증 도구가 있으며, 해당 조직 내의 모든 GitHub 사용자에게 보안 정책을 적용할 수 있다.

# 2. 사용자 ID 및 액세스 관리

인증은 엔터프라이즈의 소프트웨어 개발 에코시스템에 대한 게이트웨이이다. GitHub와 모든 사용자의 상호 작용은 ID 확인으로 시작하여 개별 계정은 사용자 이름 및 암호를 사용할 수 있지만 엔터프라이즈는 보안으로 2FA(`2단계 인증`) 또는 암호 및 생체 인식 로그인과 같은 고급 방법을 요구한다.

## 2.1 GitHub Enterprise의 최신 인증

> 안전하고 간소화된 인증 환경을 보장하기 위해 GitHub는 ID 관리 시스템과 통합되는 여러 최신 방법을 지원한다.

### 2.1.1 패스키 및 웹인증

* 패스키는 물리적 디바이스에 연결되고 피싱에 강한 암호 없는 로그인 방법이다.
* WebAuthn은 YubiKey와 같은 생체 인식 요소 및 하드웨어 토큰을 지원한다.
* 이러한 메서드는 자격 증명 기반 공격을 크게 줄이고 로그인 UX를 개선한다.

### 2.1.2 GitHub Mobile 2FA

사용자는 빠르고 안전한 승인을 위해 푸시 알림을 지원하는 GitHub Mobile을 사용하여 인증할 수 있으며 워크플로를 방해하지 않고 2FA를 향상시킬 수 있다.

### 2.1.3 OAuth 및 GitHub App

* OAuth 앱은 GitHub의 OAuth 2.0 흐름을 사용하여 사용자를 인증하고 외부 애플리케이션에 범위가 지정된 액세스 권한을 부여한다.
* GitHub Apps는 세분화된 사용 권한으로 개별 설치로 인증되며 CI/CD 및 자동화 파이프라인에 적합하다.

### 2.1.4 엔터프라이즈 관리 사용자(Enterprise Manage User)

GitHub Enterprise Cloud에서 EMU는 Idp(ID 공급자)를 통해 인증이 엄격한 단계에서 수행하도록 한다.

* 엔터프라이즈 관리 계정에 대한 액세스으로만 범위를 좁혀 제한한다.
* ID, 자격 증명 및 세션 정책에 대한 중앙 집중식 제어를 적용한다.

# 3. SAML SSO를 사용한 조직 관리

엔터프라이즈급 인증의 기본 기능 중 SAML SSO(`Single Sign-On`)으로 Idp를 GitHub와 연결하여 사용자가 하나의 자격 증명 집합을 사용하여 서비스 간에 로그인할 수 있도록 하며 조직 또는 엔터프라이즈 리소스에 대한 액세스 권한을 부여하기 전에 사용자 ID를 확인한다.

> [!IMPORTANT]
> **사용자가 GitHub에 로그인하면 속한 기업을 볼 수 있지만 리포지토리 데이터에 액세스하려면 Idp를 통한 SAML 재인증이 필요하다.**

조직에 SAML SSO를 구성하려면 Idp를 GitHup와 통합하여 다음과 같이 지원되는 공급자 형태다.

* AD FS(`Active Directory Federation Services`)
* Microsoft Entra ID
* Okta
* OneLogin
* PingOne
* 시보레스 주

> [!IMPORTANT]
> **GitHub는 SAML 2.0 표준을 구현하는 ID 공급자에 대해 제한된 지원을 제공한다.**

# 4. 엔터프라이즈 액세스 및 권한 부여 컨트룰

## 4.1 Fine-Grained PAT(개인용 액세스 토큰)

* 클래식 PAT에서 세분화된 PAT
  * 특정 리포지토리 및 범위에 대한 액세스를 제한
  * 위험 노출 감소에 대한 자동 만료를 지원
  * 향상된 추적 기능 및 규정 준수 컨트롤 제공

## 4.2 사용자 지정 리포지토리 역할

* 관리자는 기본 권한 집합 이상으로 확장되는 사용자 지정 역할을 정의할 수 있다.
  * 고유한 워크플로에 맞게 조정된 위임된 액세스
  * 중요도가 높은 리포지토리에 대한 최소 권한 적용

## 4.3 보안 정책 적용

* 모든 사용자는 2FA가 필수로 활성화 되어 있어야 한다.
* 승인된 네트워크에 대한 액세스를 제한하는 화이트 리스트[IP 허용 목록]이다.
* 명시적으로 승인되지 않은 경우 확인되지 않은 OAuth 앱을 차단한다.

## 4.4 조직 및 엔터프라이즈 수준 제어

* 조직 수준 제어에는 기본 역할, 팀 기반 액세스 및 외부 협력자의 관리가 포함된다.
* 엔터프라이즈 수준 거버넌스에는 몇 가지의 적용이 필요한 사안이 포함된다.
  * 중앙 집중식 SAML
  * Idp 기반 로그인 제한
  * GitHub Enterprise Cloud를 통한 글로벌 정책 적용

# 5. 리포지토리 표시 유형 및 내부 액세스

조직 구성원이 리포지토리를 만들 때 공용 프라이빗 또는 내부 표시 유형 옵션 중에서 선택할 수 있다.

* 공용
  * 인터넷의 모든 사용자가 사용할 수 있다.
* 비공개
  * 선택한 사용자에 한해서 제한된다.
* 내부
  * 엔터프라이즈 내의 모든 멤버에 표시되지만 외부 사용자로부터 숨겨진다.

# 6. 사용자 인증

사용자 인증에 관한 보안이 최우선 고려 사항이 되어야 하며, 강력한 보안은 권장이 아닌 필수적인 조치이다. 보안 프로세스가 비효율적이거나 회사 내에 최신 보안 기능이 없어서 자격 증명을 탈취당할 리스크가 발생하기 때문에 사용차 채택에서 인증하는 데 소요되는 시간이 길고 요청 사항 단계가 필요하다면 안전한 사용자 인증을 설정 하는 것은 난이도가 상당한 영역이다.

GitHub Enterprise는 보안 사용자 인증에 권장되는 두 가지 방법을 지원한다.

* SAML SSO (`Signle Sign-On`)
* Two-Factor (`2FA`)

## 6.1 SAML SSO 인증

SAML(`Security Assertion Markup Language`) SSO는 GitHub를 조직의 Idp(ID 공급자)와 통합하여 중앙 집중식 액세스 제어를 허용하고 규정 준수를 개선한다. 활성화 설정하면 GitHub는 조직 리소스에 대한 액세스 권한을 부여하기 전에서 인증을 위해 사용자 Idp로 리디렉션한다.

### 6.1.1 SAML SSO 사용 및 적용

> 필요한 적용 범위에 따라 조직 또는 엔터프라이즈 수준에서 SAML SSO를 구성할 수 있다. 

## 6.2 조직 수준 SAML SSO

* 설정
  * 보안 아래의 조직 설정에서 Idp의 SAML SSO URL 및 공용 인증서를 입력 후 구성을 테스트하고 저장한다.
* 적용
  * 비준수 멤버를 자동으로 제거하려면 SAML SSO 인증 필요를 선택한다.
* 사용 사례
  * 제한된 영향을 가진 단계적 롤아웃 또는 테스트에 적합하다.

> [!IMPORTANT]
> **GitHub는 인증에 실패한 조직 구성원만 제거하기 때문에 엔터프라이즈 멤버는 다음에 리소스에 액세스할 때까지 유지된다.**

## 6.3 엔터프라이즈 레벨 SAML SSO

* 설정
  * 엔터프라이즈 계정 설정에서 조직 수준과 유사하게 SAML SSO를 사용하도록 설정한다.
* 적용
  * 엔터프라이즈의 모든 조직에 SSO를 적용한다.
* 이점
  * 통합 정책을 보장하고 조각화된 구성으로 인한 위험을 줄인다.
* 참고
  * GitHub는 비규격 엔터프라이즈 멤버를 즉시 제거 하지 않으며, 액세스 시 인증요청하는 메시지가 표시된다.

| 기준        | 조직 수준         | 엔터프라이즈 수준    |
| ----------- | ----------------- | -------------------- |
| 범위        | 개별 조직         | 전체 엔터프라이즈    |
| 사용자 제거 | 적용 시 즉시 수행 | 다음 액세스까지 지연 |
| 정책 일관성 | 조직에 따라 다름  | 엔터프라이즈 간 통합 |
| 설치 복잡성 | 낮음              | 높음                 |
| 사용 사례   | 파일럿 / 테스트   | 광범위한 규정 준수   |


## 6.4 단계별 SAM OOS 사용 및 적용

* 조직
  1. 조직 → 설정 → 보안 카테고리로 이동
  2. Idp의 세부 정보로 SAML을 활성화 설정
  3. 구성을 테스트하고 저장
  4. SAML SSO 필요를 선택한 다음, 비준수 사용자를 제거

* 기업
  1. 엔터프라이즈 → 설정 → 보안 카테고리로 이동
  2. Idp의 세부 정보로 SAML을 활성화 설정
  3. 구성을 테스트하고 저장
  4. 모든 조직에서 SSO를 적용하고 비준수 사용자를 검토

# 7. 2FA(2단계 다중 인증)

2FA는 사용자 이름 및 암호 이외의 두 번재 확인 단계를 축하여 조직 구성원, 외부 협력자 및 청구 관리자에 대해 2FA를 요구할 수 있다.

> [!WARNING]
> **조직에 2단계 인증을 사용해야 하는 경우 2FA를 사용하지 않는 모든 계정이 조직에서 제거되고 해당 리포지토리에 대한 액세스 권한이 손실된다. 이는 영향을 받는 계정에는 봇 계정도 포함된다.**  
> **2FA에 대한 자세한 내용은 해당 [GitHub 2FA Docs](https://docs.github.com/ko/authentication/securing-your-account-with-two-factor-authentication-2fa)에서 찾아볼 수 있다.**

### 6.4.1 2FA 메서드

* 보안키
  * 가장 안전한 방법으로 피싱을 방지하는 물리적 USB 또는 NFC 장치, TOTP또는 SMS를 사전에 설정해야 한다.
* TOTP
  * 권장하는 수준으로 시간 기반 일회성 암호를 생성하고 백업을 지원하여 오프라인으로 작동한다.
* SMS
  * 가장 보안이 취약한 인증 수단으로 TOTP를 사용할 수 없는 경우에만 사용되어야 하며, 지역마다 기능 제공 여부가 다르다.

### 6.4.2 2FA 규정 준수 감사

* 2FA를 사용하도록 설정한 사용자를 검토하고자 한다면 다음과 같이 수행해야 한다.
  1. 조직으로 이동한 후 조직을 선택하고 → 사용자 탭을 클릭
  2. 2FA 필터 선택

> [!NOTE]
> 비규격 사용자를 식별하고 일반적으로 이메일을 통해 GitHub 외부에서 후속 조치를 수행할 수 있다.

# 8. 사용자 권한 부여

사용자가 SAML SSO를 사용하여 Idp를 통해 성공적으로 인증과정을 거친 후 권한 부여를 진행한다. 조직 리소스에 액세스할 수 있는 기능을 갖춘 PAT, SSH 키 또는 OAuth 앱과 같은 도구를 부여한다.

## 8.1 SAML SSO 및 SCIM을 사용하여 사용자 권한 부여 자동화

SAML SSO를 사용하면 엔터프라이즈 및 조직 소유자가 리포지토리, 문제 및 끌어오기 요청과 같은 GitHub 리소스에 대한 액세스를 제어할 수 잇으며, SCIM(`도메인 간 ID 관리 시스템`)을 통합하면 사용자 프로비저닝 및 프로비저닝 해제를 자동화하여 액세스 제어가 향상된다.

SCIM을 사용하면 Idp에 추가된 사용자에게 GitHub에 대한 액세스 권한이 자동으로 부여되고, 탈퇴 사용자는 제거되어 수동 프로세스 단계가 줄어들고 보안이 향상된다.

## 8.2 SAML SSO를 사용하여 SSH 키 및 PAT 관리

SAML SSO와 SCIM은 GitHub의 ID 변경 내용을 반영하기 위한 장치로 작동하며 이 기능을 제공 받고자 한다면 다음과 같이 수행해야 한다.

* SAML Idp와 SCIM 클라이언트 간에 NameID 및 userName이 일치해야 한다.
* GitHub에서 Idp 트리거 SCIM 업데이트의 변경 내용을 그룹화한다.

> API 또는 Git에 액세스하는 사용자는 권한 있는 PAT 또는 SSH 키를 사용해야 하며, 메서드는 감사 가능하고 SAML SSO에 안전하게 연결해야 한다.


# 9. GitHub와 SCIM 통합

SCIM은 네이티브 통합 및 사용자 지정 구성을 모두 지원하여 GitHub Enterprise Cloud에서 ID 관리를 간소화한다.

## 9.1 지원되는 SCIM 공급자

* Okta
* Microsoft Entra ID
* OneLogin
* Ping Identity
* Google Workspace

## 9.2 사용자 지정 SCIM 통합

Idp가 기본적으로 지원되지 않는 경우 GitHub의 SCIM API를 사용하여 사용자 지정 통합을 빌드한다.

### 9.2.1 SCIM API 개요

SCIM 2.0 API를 사용하면 다음과 같이 수핼할 수 있다.

* 사용자 생성, 업데이트 및 삭제
* 그룹 관리

### 9.2.2 사용자 프로비전 요청 예제

# 10. SCIM 시작 프로세스

* 지원되는 공급자의 경우
  1. Idp 관리 콘솔에 로그인 진행
  2. SCIM 프로비저닝을 활성화 설정
  3. GitHub의 SCIM 기본 URL 및 전달자 토큰 제공

* 사용자 지정 IDP의 경우
  1. GitHub의 SCIM REST API를 사용
  2. PAT를 사용하여 인증
  3. 샘플 요청과의 통합 테스트 진행

## 10.1 SCIM 통합의 주요 이점

* 프로비저닝
  * 계정을 자동으로 생성한다.
* 업데이트
  * 역할 및 부서를 동기화한다.
* 프로비전 해제
  * 사용자가 종료되면 즉시 액세스를 제거한다.

## 10.2 SCIM 및 수동 사용자 관리

| 측면      | SCIM 기반 관리                              | 수동 관리                       |
| --------- | ------------------------------------------- | ------------------------------- |
| 자동화    | 프로비저닝 및 프로비전 해제 자동화          | 수동 개입 필요                  |
| 일관성    | 시스템 간 표준화된 사용자 데이터            | 불일치 위험                     |
| 보안      | 적시에 액세스 비활성화                      | 지연되거나 누락된 해지          |
| 확장성    | 대규모 사용자 기반을 사용하여 스케일 조정   | 스케일이 크면 복잡성 증가       |

# 12. 팀 동기화

회사에서 Idp로 Microsoft Entra ID 또는 Okta를 사용하는 경우 팀 동기화를 통해 GitHub 팀 멤버 작격을 관리할 수 있기에 활성화 설정하면 팀 통기화는 그룹의 변경 내용을 자동으로 반영하여 수동 업데이트 또는 사용자 지정 스크립트의 의존성을 줄일 수 있다. 이 중앙 집중식 접근 방식은 온보딩, 권한 관리 및 액세스 해지를 간소화할 수 있다.

| 특징                | 설명                                                                         |
| ------------------- | ---------------------------------------------------------------------------- |
| 사용자 동기화       | GitHub Teams를 Idp(AD : `Active Directory`) 그룹 멤버 자격과 일치하도록 유지 |
| 새 팀에서 동기화    | 생성 시 팀을 자동으로 배정                                                   |
| 사용자 지정 팀 매핑 | 팀 슬러그와 그룹 이름 간에 사용자 지정 매핑을 정의하는 데 사용               |
| 동적 구성           | `settings` 파일을 사용하여 디렉터리 구조에서 동기화 설정 파생                |

## 12.1 팀 동기화 사용 사례

팀 동기화는 조직 내에서 멤버 자격 관리를 간소화려는 기업에 적합하여 관리자는 팀을 Idp 그룹에 매핑하고 멤버 자격을 자동으로 관리할 수 있기 때문에, 이 기능은 다음과 같은 경우에 활용도가 높다.

* 신입 멤버 온보딩
* 사용자가 팀 간에 이동할 때 액세스 조정
* 조직을 떠나는 사용자 제거

> [!WARNING]
> **팀 동기화를 사용하려면 사전에 Idp 관리자가 SAML SSO 및 SCIM을 사용하도록 설정해야 한다.**

# 13. 엔터 프라이즈 관리 사용자 및 GitHub Enterprise Server

GitHub Enterprise Cloud 또는 Server를 사용하는 조직 및 엔터프라이즈 계정에서도 팀 동기화를 이용할 수 있다. 이는 규정 준수를 위해 사용 가능하거나 필요한 지역에서 선호하는 솔루션이다. EMU(Enterprise Managed Users) 는 엔터프라이즈가 사용자 ID 및 계정 수명 주기를 완벽하게 제어할 수 있도록 하는 GitHub Enterprise Cloud 기능이며, GitHub 계정이 엔터프라이즈 ID 공급자에 의해 완전한 관리가 된다. 사용자는 GitHub에 직접적으로 등록하지 않고, 프로비저닝, 액세스 및 오프보딩은 Microsoft Entra ID 또는 Okta와 같은 도구를 통해 자동화 한다.

> EMU는 엄격한 규정 준수, 감사 또는 사용자 거버넌스 요구 사항이 있는 조직에 적합하며 이는 다음을 수행할 수 있다.

* 모든 계정은 엔터프라이즈가 소유한다.
* Idp 멤버 자격에 따라 액세스 권한이 자동으로 부여되거나 제거된다.
* 의도치 않게 외부 협업이 발생하지 않는다.

또한, EMU를 사용하는 동안에는 다음과 같은 상황이 발생할 수 있다.

* 관리되는 사용자는 엔터프라이즈 외부의 리포지토리에 코드를 푸시하거나 포크할 수 없다.
* 엔터프라이즈 내의 다른 사용자 및 리소스와만 상호 작용할 수 있다.

> [!NOTE]
> **Idp의 그룹을 사용하여 EMU 기반 조직 및 팀 멤버 자격을 관리하고 필요에 따라 팀 동기화를 통합하여 그룹 간 매핑을 자동화할 수 있다.**  
> **자체 호스팅 또는 특정 지역 규정과 관련된 요구 사항이 있는 조직의 경우 GitHub Enterprise Server는 GitHub 환경을 완전한 제어할 수 있는 온-프레미스 솔루션을 제공한다.**

# 14. 팀 동기화와 GHES용 SCIM 비교

GHES(GitHub Enterprise Server)에서 팀 동기화 및 SCIM(도메인 간 ID 관리)을 비롯한 다양한 방법을 통해 사용자 액세스 및 팀 멤버 자격을 관리할 수 있다. 

## 14.1 GHES의 팀 동기화

팀 동기화를 사용하면 Idp의 그룹과 GitHub 팀을 연결할 수 있고, 이 통합을 통해 멤버 추가 또는 제거와 같은 Idp 그룹의 모든 변경 내용이 해당 GitHub 팀에 자동으로 반영된다. 이 프로세서의 Idp 내에서 사용자 액세스 제어를 중앙 집중화하여 팀 관리를 간소화한다.

하지만 팀 동기화는 사용자 프로비저닝 서비스가 아니기 때문에 대부분의 경우 비회원이 조직에 가입하도록 초대하지 않는다는 점에 유의해야 하고 따라서 사용자는 이미 조직 구성원인 경우에만 팀에 성공적으로 추가된다.

> [!IMPORTANT]
> **GHES의 팀 동기화는 계정을 프로비전하지 않기 때문에 사용자는 이미 GitHub 조직 구성원이어야 한다.**

> [!TIP]
> **팀 동기화가 실제로 작동하는 방식을 이해하려면 다음 시나리오를 고려하세요.**
> * **Azure AD 그룹 "DevOps 엔지니어"가 GitHub 팀 "DevOps"에 매핑되는 경우**
> * **Alice가 IdP 그룹에 추가되면 → GitHub 팀에 자동으로 추가**
> * **사용자가 그룹을 떠날 때 → 자동으로 팀에서 제거**

### 14.1.1 팀 동기화 사용

1. Idp에서 SAML(Security Assertion Markup Language) SSO(Single Sign-On) 및 SCIM을 사용하도록 설정
2. GitHub UI 또는 API를 통해 GitHub 팀을 Idp 그룹에 매핑
3. 그룹 멤버 자격의 변경 내용이 GitHub에 자동으로 동기화

# 15. GHES의 SCIM

SCIM은 ID 도메인과 IT 시스템 간의 사용자 ID 정보 교환을 자동화하도록 설계된 개방형 표준 프로토콜이다. GHES의 컨텍스트에서 SCIM을 사용하면 관리자가 GitHub API를 통해 직접 사용자가 계정을 프로비전, 업데이트 및 프로비저닝 해제할 수 잇으며, 사용자 계정을 생성, 업데이트, 제거, 그룹 정보 통기화하여 GitHub 팀 멤버 자격을 매핑할 수 있다.

SCIM은 사용자 수명 주기를 대규모 단위로 관리하여 사용자 데이터가 시스템 간에 일관성을 유지하도록 하는 데 유용하다.

> [!IMPORTANT]
> **SCIM이 실제로 작동하는 방식을 이해하고자 한다면 다음 시나리오를 참고하면 된다.**
> * **Okta SCIM 통합은 GitHub 사용자를 자동으로 프로비전 진행**
> * **사용자가 Okta에 추가되면 GitHub 계정이 프로비저닝 완료**
> * **사용자의 직무 변경 → 액세스 권한 및 팀 업데이트**
> * **사용자의 팀 탈퇴 → 계정 프로비전 해제**
