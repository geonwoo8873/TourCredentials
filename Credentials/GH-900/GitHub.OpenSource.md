# GitHub Project Open Source Contribute

> [!NOTE]
> 오픈 소스 소프트웨어는 공개적으로 사용 및 수정과 공유를 통해 어떤 용돌로도 프로젝트를 보고 수정하며 배포까지 가능하기 때문에 오픈 소스 소프트웨어의 뒷받침 개념은 공유함으로써 신뢰할 수 있는 더 나은 소프트웨어를 끌어낼수 있다는 목표로 생긴 문화이다.

## 기여가 필요한 오픈 소스 프로젝트 검색

모둔 오픈 소스의 프로젝트들은 같은 최신화가 업데이트 진행 되어있지 않아, 항목이 예상대로 작동하지 않거나 설명서가 일부 오타 및 링크를 찾을 수 없는 경우가 있기 때문에 이는 모두 프로젝트를 지원하고 기여하는 데 유용한 기회이다. `모든` 종류의 기여는 유용하며, 경험 수준이나 프로젝트에 관한 지식은 다소 중요하지 않더라도 누구나 기여할 수 있는 무언가가 있으며, 핵심 적인 부분은 지원하겠다는 목표를 추구하는 것이다.

### GitHub 검색

GitHub.com에서 상단 윗 부분에 검색란이 있다. 이는 리포지토리, 코드, 커밋, 문제, 토픽, 패키지 등 다양한 핉터를 통해서 기여 가능한 프로젝트가 있다면 지원이 가능하며 최신순, 즐겨찾기 등 사용자가 협업 과정을 구축하는 방법을 제공하고 있다.

### 오픈 소스 프로젝트 기여

해당 기여하고자 하는 프로젝트에는 모든 기여 지침과 보안 규모가 다르기 때문에 필수로 숙지해야 하며 다음과 같이 최상위 루트에서 관련 문서가 작성되어 있다.

* 라이선스
  * 플로젝트에 오픈 소스 라이선스가 포함되어야 하며, 프로젝트에 라이선스가 없는 경우 오픈 소스가 아니다.
* 추가 정보
  * READE 파일은 일반적으로 프로젝트의 시작 페이지 역할을 맡고 있으며, 플로젝트 사용을 시작하는 방법이나 기여하는 방법에 대한 지침 가이드를 포함한다.
* 기여
  * 문서에서는 프로젝트에 기여하는 방법에 대한 지침을 제공합니다. 일반적으로 기여 프로세스가 작동하는 방법을 기재하여 설명하고 개발 환경 설정하는 자세한 방법을 포함한다.
* CODE_OF_CONDUCT
  * 행동 강령은 구성원에 대한 기본 규칙을 설정하고, 커뮤니티를 안전하고 환영받을 수 있는 긍정적인 방향으로 만드는 데 도움이 된다. 하지만 모든 문서에는 행동 강령이 있는건 아니지만 해당 문서는 플로젝트가 얼마나 친숙하고 환영받는지를 보여 주는 지표이다.

오픈 소스 기여자 및 유지 관리자는 전 세계에서 유입되며 프로젝트에는 일반적으로 토론을 구성하고 도움을 요청하기 위한 여러 소통 채널이 있으며, 커뮤니티를 이해하는 데 좋은 방법은 관련 소통 채널을 읽는 것이다. 다음과 같이 커뮤니티에 기여 및 소통 방식은 제공된다.

* 문제 추적
  * 프로젝트와 관련된 문제 및 작업을 논의하는 위치이며, GitHub에서 문제를 찾고자 하며 리포지토리의 기본 페이지로 이동하여 해당 URL 주소 마지막에 `/issue`를 추가하면 된다.
* 풀 리퀘스트
  * 프로젝트의 변경 사항을 사람들이 논의하고 검토하는 곳이며, 프로젝트의 URL에 `pulls`를 추가하여 GitHub에서 찾을 수 있다.
* 소통 채널 및 포럼
  * 일부 프로젝트는 Slack, Gitter 및 IRC와 같은 채팅 채널 또는 대화 및 토론을 위해 담론과 같은 포럼을 사용한다.

### 기여할 작업 식별

수행할 작업을 파악이 완료 되었다면, 문제를 찾는 방법 중 하나는 `/contribute`을 방문하는 것이다. URL에 표시되는 대부분의 문제는 `good-first-issue`, `help wanted`, `beginner-ffriendly`와 같은 레이블들이 구성되어 있으며, 레이블은 문제에 대한 최상위 정보와 필요한 지원 유형을 제공하는 데 자주 사용된다.

레이블 페이지는 `github.com/${repo}$/${issue}$/labels`로 이동할 수 있으며, 관심 있는 유형에 ㄹㄹ레이블이 있는 문제를 선택할 수 있다. 문제를 탐색할 때 일부 문제에 다른 문제나 끌어오기 요청이 연결된 것을 확인이 가능하다.

### 프로젝트 스폰서

오픈 소스에 기여하는 방법중 스폰서 후원은 코드, 리더십, 멘토십, 설계 등을 통해 오픈 소스 에코시스템을 빌드하고 유지관리하는 담당자를 재정적 지원할 수 있다. 오픈 소스는 지원에 크게 의존하기 때문에 `GitHub Sponsors`를 사용하면 프로젝트와 개인에게 자금을 제공하여 원하는 인정을 제공 하면서 오픈 소스 작업을 유지하도록 지원한다.

## 오픈 소스 리포지토리 기여

지원자는 기여할 수 있는 영역을 파악한 후 기여 준비를 거치는데, 이는 프로젝트 기여 의도를 전달하고, 끌어오기 요청을 요청하며 수락받을 확률을 높일수 있게 된다. 프로젝트에 대한 기여 작업에서는 양방향 소통이 주요 성공 요인으로 발견되고 있으며, 제안된 변경 사항 또는 개선 사항을 다른 사용자에게 전달하는 것이 불편할ㄹ 수 있기 때문에 대와는 방향성에 대한 논의와 타협으로 이어질 수 있다.

오픈 소스 프로젝트와 관련된 다른 사용자들과의 활발한 소통을 피하면 이미 작업 중인 사용자와 작업을 하는 시간을 불필요한 소모 위험이 발생하기 때문에, 프로젝트의 가치나 모범 사례와 맞지 않는 기능 또는 개선 기능을 위해 작업할 수도 있다. 두 경우 모두 앞에 서술된 것처럼 리스크에 대한 상승 확률이 존재하여, 적극적으로 소통하는 과정에서는 사용자의 작업이 올바르게 수신되고 있다는 반영을 보여준다.

### 관리자에게 의도 전달

실제 작업을 수행준비 단계에서 항상 기여 의도를 전달하는 것으로 시작해야 한다. 추가 정보 파일에 달리 표시되지 않는 한 일반적으로 문제 추적기에서 작업을 수행하는 것이 가장 좋다. 

* 기존 문제를 해결하려면 할당자 섹션을 확인하여 할당된 사람이 없는지 확인한다. 연결된 끌어오기 요청 섹션도 확인하여 연결된 끌어오기 요청은 외부 사용자가 이미 작업하고 있음을 의미한다. 댓글을 검토하여 해당 문제에 대해 관심을 표현한 지원자가 있는지 확인하고, 모든 사항을 확인한 후 게시하여 문제에 대한 관심을 표현한다.
* 문제 추적기에 아직 표시되지 않은 새로운 기능 또는 버그를 처리하고자 한다면 새 문제를 생성 후 템플릿을 따르고 문제에 대한 작업 의도를 명시적을로 표현해야 한다.

### GitHub 리포지토리에서 끌어오기 요청 만들기

이전에 관리자에게 의도를 전달을 진행 후에 끌어오기 요청을 게시하여 하나의 기여 형태를 취하는 것이다. 다음과 같이 PR에 대해서 여러 항목이 포함되는 위치이다.

* 변경 내용에 대한 제목 및 설명
* 제안하는 변경 사항을 이루는 하나 이상의 커밋
* 댓글에는 모든 사람이 변경 내용에 대한 논의에 참여
* 코드 검토는 변경 내용에 대한 자세한 피드백을 찾아보고 제안을 커밋할 수 있다.
* 상태 검사에서 유지 관리자가 준비한 자동화된 테스트에서 생성되었으며, 상태 검사는 다른 용도로도 사용이 가능하기 때문에 변경 내용이 프로젝트의 규칙을 따르고 변경으로 인해 코드가 중단되지 않는지 확인할 수 있다.

끌어오기 요청이 생성된 후에는 커밋, 댓글 또는 코드 검토를 통해 해당 요청을 업데이트할 수 있으며, 이 프로세스는 퍼블릭 리포지토리를 변경할 권한이 없으므로 이 단계를 수행해야 한다. 프로젝트를 포크하여 변경할 수 있는 복사본을 생성한다.
