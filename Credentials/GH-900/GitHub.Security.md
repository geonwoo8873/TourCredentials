# GitHub Repository Security Manage

## 1. 보안 GitHub 리포지토리 유지 관리 과정

애플리케이션 보안의 중요성은 보안 개발 전략을 계획할 때 고려해야할 문제와 직결되고 외부에 정보가 공개되지 않도록 보호해야 하지만 적절한 경우에만 변경되거나 삭제되도록 해야 한다. 또한 데이터는 액세스하는 사용자와 데이터에 액세스할 수 잇는 올바른 권한이 있는지 명확한 검증이 되어야 하며, 기록 또는 보관 데이터 또는 로그를 통해 문제가 있을 때 증거를 찾을 수 있어야 한다.

해당 애플리케이션을 빌드하고 배포하는 데는 여러 가지 측면이 존재하며, 고래야할 사항은 다음과 같다.

* **일반적인 지식 문제가 발생한다.** 다수의 개발자와 그외 이해관계자들은 보안을 숙지하고 있는 형태로 가정하지만 현실적으로 그렇지 않으며, 사이버 보안은 지속적으로 보완과 진화하는 분야에 속하기 때문에 지속적인 교육 및 교육 프로그램은 필수적이다.
* **코드를 정확하고 안전하게 만들어야 한다.** 코드가 올바르게 생성되고 필요한 기능을 안전하게 구현해야 하는 목표를 가지고 있기 때문에, 보안을 염두에 두고 기능이 설계되어 있는지 모니터링이 필요하다.
* **애플리케이션은 규칙 및 규정을 준수해야 하며, 코드가 필요한 규칙 및 규정을 준수하는지 검증을 진행한다.** 코드를 빌드하는 동안 규정 준수를 테스트한 다음 배포 후에도 주기적으로 재 테스트 과정을 거치는 것이다.

### 1.2 모든 단계의 보안

보안은 향후 애플리케이션 또는 시스템에 추가할 수 있는 것이 아닌 소프트웨어 개발 수명 주기의 전과정에서 속해야 하며, 이 개념은 중요한 애플리케이션 및 중요한 또는 극비 정보를 처리하는 애플리케이션에 더욱 중요하다. 실사례를 바탕으로 팀이 개발한 내용에 대한 책임을 보다 명확하게 묻기 위함으로 프로세스는 왼쪽으로 이동하거나 개발 수명 주기 초기에 완료해야 한다. 배포시 최종 게이트에서 이전 단계로 단계를 이동하면 실수를 방지할 수 있을뿐만 아니라 더 빠른 대응이 가능하도록 이동이 가능하다.

또한 애플리케이션 보안 개념은 과거에는 개발자에게 중점을 두지 않았었다. 교육 및 교육 문제 외에도 조직에서 기능외 빠른 개발을 강조해왔고 그에 따른 비용 발생에 따른 외부적인 과정이 추가되기 때문에 생긴 현상이다. 그러나 현재는 DevOps 사례가 도이보디면 보안 테스트를 파이프라인에 더 쉽게 통합할 수 있도록 하고, 보안 전문가가 수행하는 작업이 아니라 보안 테스트는 일상적인 배달 프로세스의 일부뿐이다.

전반적으로 재작업 시간을 고려할 경우 개발 수명 주기의 앞부분에서 DevOps 사례에 보안을 추가하면 개발 팀이 문제를 빠르게 파악할 수 있으며, 문제를 보다 빠르게 인지할 수록 고품질의 소프트웨어를 개발하는 데 발생하는 전체적인 시간을 단축 시킬수 있는데 장점을 가지고 있다. 

## 2. 제공되는 보안 카테고리의 기능들

GitHub는 리포지토리 및 조직 전체에서 데이터를 안전하게 유지하는 데 도움이 되는 보안 기능들을 제공하며, 해당 리포지토리의 보안 탭에서 찾아 수행 가능하다.

* GitHub.com 리포지토리의 기본 페이지로 이동
* 리포지토리 이름 하단에 보안 카테고리 선택
  
보안 탭에서는 GitHub 워크플로에 기능을 추가하여 리포지토리 및 코드베이스의 취약성을 방지할 수 있다. 이러한 기능은 다음과 같이 권장 사항이다.

* 리포지토리에 파일을 추가하여 프로젝트에서 보안 취약성을 보고하는 방법을 지정할 수 있는 `SECURITY.md` 설정 가능
* GitHub에서 리포지토리가 취약한 종속성 또는 맬웨어를 사용하고 있음을 감지할 때 사용자에게 알리는 `Dependabot` 경고
* 리포지토리의 보안 취약성에 대한 정보를 비공개로 논의, 수정 및 계시하는 데 사용할 수 잇는 보안 권고
* 코드에서 취약성 및 오류를 찾고, 심사하며 수정하는 데 도움이 되는 코드 검사
* 리포지토리에 커밋된 토큰, 자격 증명 및 비밀을 검색하고 푸시 전에 차단할 수 있는 비밀 검사로서, 푸시 보호는 공용 리포지토리에서 기본적으로 사용하도록 설정

### 2.2 SECURITY.md 보안 정책 전달

GitHub의 커뮤니티는 잠재적인 리스크를 따른다. 공개적으로 제한없이 버그 수정을 제안할 수 있음과 동시에 특정 책임과 함께 제공되기 때문에 기본 버그를 수정하기 전에 보안 악용으로 이어질 수 있는 정보의 책임 있는 공개이다. 개발자는 보안 문제를 보고하거나 해결하기 위해 리포지토리의 루트에 있는 파일 `SECURITY.md`을 찾아 문제를 공개하고 지침을 제공하면 궁극적으로 중요한 문제를 신속하게 대응할 수 있다.

### 2.3 GitHub 보안 공지

GitHub Security Advisories를 사용하면 리포지토리 유지 관리자가 프로젝트의 보안 취약성을 비공개로 논의하고 수정할 수 있다. 리포지토리 유지 관리자는 수정에 대해 공동 작업한 후 보안 권고를 게시하여 보안 취약성을 프로젝트 커뮤니티에 공개적으로 게시할 수 있으며, 리포지토리 유지 관리자는 보안 권고를 게시해 커뮤니티에서 패키지 종속성을 보다 쉽게 업데이트하고 보안 취약성의 결과를 연구할 수 있도록 한다. 게시된 권고를 CVE(`Common Vulnerabilities and Exposures`) 목록에 저장하여 이 목록은 나열된 취약성이 있는 소프트웨어를 사용하는 영향을 받는 리포지토리에 자동으로 공유하는 데 사용된다.

## 3. .gitignore 활용하여 리포지토리의 기밀 파일 푸시 방지

개발자는 커밋에 포함된 파일을 쉽게 간과할 수 잇다. 간과된 파일은 중간 빌드 파일과 같이 무해한 경우도 있지만 누군가가 실수로 중요한 데이터를 커밋할 가능성은 언제나 위험성이 뒷따르기 때문에 악의적인 행위를 방지하고자 API키 같은 프라이빗 구성 데이터를 커밋하지 않도록 설정할 수 있다. 이러한 위험을 방지하는 것이 파일을 빌드하고 유지 관리하는 `.gitignore` 구성 파일의 역할이며 `git` 명령줄 유틸리티와 같은 클라이언트 도구에 경로와 패턴을 무시하도록 지시하여 커밋을 위한 파일을 집계한다.

```gitignore
# Directory root ignore
**/path/to/ignore/

# File ignore
**/file_to_ignore.txt

# Ignore all .log files
**/*.log
```

> [!NOTE]
> **리포지토리에 여러 `.gitignore`의 구성 파일이 포함될 수 잇지만 설정은 대체적으로 최상위 디렉터리에서 상속되 새 파일의 구성 파일보다 우선된다. 하나의 `.gitignore` 파일을 유지 관리하는 것은 굉장한 시간과 노력이 필요로 하지만, 특정 요구 사항이 있는 프로젝트에서 별도로 관리하기 쉬운 파일 경우에는 프로젝트 디렉터리에 추가하는 것이 도움될 수 있다.**

### 3.2 리포지토리에서 데이터 제거

기여자가 중요한 기밀 데이터를 커밋하지 않도록 돕는 데 파일이 일시적으로 유용할 수 있지만, 이는 곧 권고사항일 뿐이지만 개발자는 의도적으로 `.gitignore` 파일의 제한을 우회하여 커밋이 가능하기 때문에, 파일 구성을 충족하지 않아서 의도치 않는 제한에 포함되지 않을 수 있다. 그렇기에 프로젝트 참가자는 항상 리포지토리 또는 해당 기록에 포함되지 않아야 하는 데이터를 포함하는 커밋을 경계해야 한다.

> [!WARNING]
> **언제든 GitHub에 커밋된 모든 데이터가 손상 가능성이 존재한다고 가정해야 하며, 커밋을 덮어쓰는 것만으로는 향후에 데이터 액세스할 수 없도록 하는 것만으로 충분하지 않다.**

## 4. CODEOWNERS 파일 추가

리포지토리에 `CODEOWNERS` 파일을 추가하여 개별 팀 또는 구성원 및 전체 팀을 리포지토리의 경로에 코드 소유자로 할당할 수 있으며, 코드 소유자는 구성된 경로의 파일 변경 내용에 대한 끌어오기 요청 검토가 필요하다.

* Example CODEOWNERS
    ```
    # Changes to files with the js extensions need to be reviewed by the js-owner user/group:
    *.js    @js-owner

    # Changes to files in the builds folder need to be reviewed by the octocat user/group:
    /build/ @octocat
    ```

## 5. 보안 취약성으로 오래된 종속성 검색 및 수정

대체로 프로젝트에서는 외부 패키지에 종속되면서 구성 요소는 생산성에 상당한 비중을 차지함 동시와 이점을 제공할 수 있지만 다른 보안 위험을 초래할 수 있기 때문에, 각 종속성에 추적 및 유지 관리에 있어 복잡도가 상승함 으로써 해당 취약성 상태를 유지하는 데 시간이 발생할 수 있다.

### 5.2 리포지토리 종속성 그래프

모든 리포지토리에 포함된 기본 기능 중 하나는 종속성 그래프이며, GitHub는 일반적인 패키지 매니페스트를 검색하고, 그래프를 사용하면 프로젝트 소유자가 프로젝트에 의존하는 모든 종속성을 재귀적으로 추적이 가능햐다.

### 5.3 Dependabot 경고

시각적 종속성 그래프를 사용하더라도 프로젝트에 있는 모든 종속성에 대한 최신 보안 고려 사항을 유지하는 것은 여전히 압도적일 수 있다. 오버헤드를 줄이기 위해 종속성 그래프를 감시 및 추적하는 `Dependabot` 경고를 제공하며, 알려진 취약성 목록의 버전과 대상 버전을 상호 참조한다. 위험이 발견되면 프로젝트에 경고가 표시되고, 분석에 대한 입력은 `GitHub 보안 권고`에서 제공된다.

#### 5.3.2 Dependabot을 사용한 자동화 종속성 업데이트

종속성 경고로 인해 프로젝트 기여자가 권장 버전에 잘못된 패키지 참조를 변경하고 유효성 검사 끌어오기 요청을 생성할 수 있다. 이러한 과정을 자동화할 방법이 있다면 개발 속도에 유리한 장점이 될 수 있으며 이는 GitHub에서 기능을 제공한다. 종속성 경고를 검색하고 끌어오기 요청을 생성해 참가자가 업데이트의 유효성을 검사하고 요청을 병합할 수 있도록 한다.

### 5.4 자동화 코드 검사 [CodeQL]

`Dependabot`이 리포지토리에서 종속성 경고를 검색하는 방법과 마찬가지로, 코드 검색을 사용하여 GitHub 리포지토리의 코드에서 보안 취약성 및 오류를 분석하고 찾을 수 있다. 코드 검색에는 다양한 이점을 제공하며 이를 사용하여 기존 문제 또는 잠재적인 보안 취약성에 대한 수정 사항을 찾고, 심사하여 우선 순위를 지정할 수 있다.

코드 검사의 또 다른 이점은 CodeQL의 기능을 사용하는 것이고 코드를 데이터로 쿼리할 수 있으므로 사용자 지정 쿼리를 만들거나 오픈 소스 커뮤니티에서 유지 관리하는 쿼리를 사용할 수 잇다. 코드 검색을 사용하여 리포지토리 내의 코드를 검사하는 방법을 자유롭게 사용자 지정하고 유지 관리가 가능하다.
