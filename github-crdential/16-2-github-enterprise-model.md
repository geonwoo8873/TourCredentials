# 1. GitHub Enterprise 모델 이해 [`GH-100`]

## 1.1 사용자가 관리되는 방법

GHEC(GitHub Enterprise Cloud)는 엔터프라이즈급 보안 및 규정 준수를 유지하면서 인프라의 유연성과 확장성이 필요한 조직에 맞게 조정된 클라우드 기반 솔루션이다. 중앙 집중식 사용자 관리, 데이터 상주 옵션, Single Sign-On 및 사용자 프로비저닝을 위한 SAML 및 SCIM과 같은 ID 공급자와의 통합과 같은 기능을 제공한다.

GHEC는 고가용성, 백업 자동화 및 GitHub의 공동 작업 도구에 대한 원활한 액세스를 보장하므로 전역적으로 분산된 팀에 적합하고, 규정 준수를 지원해 거버넌스에 대한 자세한 감사 로그를 제공한다. 이에 대한 조직은 온-프레미스 인프라를 관리하지 않고도 GitHub의 고급 기능을 활용할 수 있다.

### 1.1.1 표준 사용자 모델

사용자가 자신의 계정을 관리하는 GitHub의 기존 사용자 모델이다.

**표준 사용자 모델의 특징** :
* 사용자는 사용자 이름, 전자 메일 주소 및 개인 설정을 포함하여 자신의 계정을 관리한다.
* 인증 방법은 사용자가 구성한다.
* 조직 또는 엔터프라이즈 계정에 대한 연결은 초대를 통해 설정된다.
* 관리자는 엔터프라이즈 조직에 연결되면 사용자 계정을 제한하여 제어할 수 있다.
* 엄격한 중앙 집중식 관리 요구 사항이 없는 소규모 기업 또는 조직에서 자주 사용된다.

### 1.1.2 EMU 모델

중앙 집중식 사용자 계정 관리가 필요한 조직을 위한 설계된 모델로 보다 더 나은 제어 및 규정 준수 기능을 제공한다.

**EMU 모델은 다음과 같이 프로세스가 제공된다.**
* 사용자 계정은 엔터프라이즈에서 완전히 관리된다.
* 인증은 엔터프라이즈의 ID 공급자를 통해 처리된다.
* 관리자는 사용자 이름, 이메일 주소 및 사용자 수명 주기를 제어할 수 있다.
* 관리되는 사용자는 속한 엔터프라이즈에만 가입할 수 있으며 다른 조직에 독립적으로 가입할 수 있다.
* 더 엄격한 거버넌스 정책을 준수해야 하는 대기업 또는 조직에서 자주 사용된다.

# 2. GitHub Enterprise Cloud(GHEC) Data Residency 사용 [`GH-100`]

Data Residency를 사용하는 GHEC는 특정 데이터가 특정 지리적 지역에 저장되도록 하여 데이터 보호 규정을 준수해야 하는 조직을 위한 기능이며, 이를 통해 사용자는 다음을 수행할 수 있다.

1. **데이터 상주 지역**
   * GitHub는 규정 준수 요구 사항에 따라 미리 정의된 지역을 제공한다.
2. **다루는 데이터 형식**
   * **리포지토리 콘텐츠** : 코드, 문제, 끌어오기 요청 및 리포지토리 관련 데이터이다.
   * **메타데이터** : 감사 로그, 사용자 이벤트 및 설정을 포함한다.
3. **암호화 및 보안**
   * 전송 중 및 미사용 데이터는 모두 암호화된다.
   * 지역 및 글로벌 보안 표준 준수(ex: ISO 27001, SOC 2)
4. **지역별 스토리지 및 장애 조치**
   * 데이터는 고가용성 및 재해 복구 메커니즘을 사용하여 선택한 지역에 저장된다.
   * 특정 유형의 백업 데이터는 지역 외부에서 복제될 수 있지만 암호화된 상태로 유지된다.

# 3. GitHub Enterprise Server(GHES) [`GH-100`]

GHES는 GitHub 인스턴스를 온전히 제어해야 하는 조직을 위해 설계된 자체 호스팅 버전의 GitHub이다. 규정 준수, 보안, 성능상의 이유로 온-프레미스 또는 프라이빗 클라우드 환경에서 리포지토리 및 관련 데이터를 호스트하려는 회사에 적합하다.

## 3.1 GitHub Enterprise Server의 주요 기능

1. **자체 호스팅**
   * 조직의 인프라 내에서 온-프레미스 또는 프라이빗 클라우드에 배포된다.
   * 데이터 스토리지, 백업 및 재해 복구에 대한 모든 권한을 제공한다.
2. **향상된 보안**
   * 데이터는 조직의 환경 내에 유지되므로 엄격한 데이터 보존, 개인 정보 보호 또는 보안 요구 사항을 준수할 수 있다.
   * 엔터프라이즈 인증 시스템(LDAP, SAML SSO, Active Directory)과 통합된다.
3. **사용자 지정 및 제어**
   * 리포지토리 설정, 사용자 액세스 및 권한을 완전히 제어한다.
   * 내부 DevOps 도구 또는 CI/CD 파이프라인과 같은 사용자 지정 통합 및 확장을 허용한다.
4. **성능 최적화**
   * 대규모 리포지토리 또는 분산 팀이 있는 조직에 최적화되어 있다.
   * 추가 리소스를 할당하여 과도한 워크로드를 처리하도록 크기를 조정할 수 있다.
5. **규정 준수**
   * 엄격한 규제 요구 사항이 있는 산업에 적합하다.
   * 규정 준수 표준을 충족하기 위해 감사 로그, 사용자 활동 모니터링 및 데이터 암호화를 제공한다.

## 3.2 GitHub Enterprise Server의 구성 요소

1. **GitHub Application**
   * 인터페이스 및 핵심 기능은 기존의 GitHub.com과 유사하다.
2. **관리 대시보드**
   * 사용자, 팀 및 조직을 관리하기 위한 도구를 제공한다.
   * 리포지토리 액세스, 백업 및 업데이트에 대한 설정을 포함한다.
3. **시스템 관리 도구**
   * 서버 구성, 리소스 할당 및 성능 모니터링을 관리하기 위한 도구이다.
4. **백업 및 재해 복구**
   * 데이터 손실을 방지하기 위해 백업을 만들고 복원하는 기능이다.
5. **모니터링 및 로깅**
   * 서버 상태를 위한 Prometheus 및 Grafana와 같은 시각 데이터 제공 모니터링 도구이다.
   * 문제 해결 및 감사에 대한 로그이다.

# 4. 작업 및 워크플로 관리 [`GH-100`]

## 4.1 엔터프라이즈 수준

### 4.1.1 GitHub Actions 사용 정책 구성

워크플로에는 일반적으로 워크플로 내에서 실행할 독립 실행형 명령의 집합인 작업이 포함된다. 워크플로를 생성할 때 Marketplace에서 제공하는 공용 커뮤니티 작업을 사용하거나 참조할 수 있는 사용자 고유 작업을 생성할 수 있다. 이러한 이류로 기업의 워크플로 및 작업에 대한 사용 정책을 구성하는 것은 사용자가 악의적으로 행하는 목적으로 타사 작업을 사용하지 못하도록 하는 데 필수적이다.

1. 엔터 프라이즈 설정에서 GitHub Connect를 사용하도록 설정된 경우, Enterprise Cloude 및 Enterprise Server에서 정책을 구성하기 위한 여러 옵션이 있다. GitHub Actions를 구성하려면 해당하는 엔터프라이즈 계정으로 이동하여 정책 선택 후 작업으로 이동하면 된다.
2. 모든 조직에서 사용이라는 상단 위에 있는 드롭다운에서 GitHub Actions를 사용할 수 있는 엔터프라이즈의 조직을 결정하고 옵션을 사용하여 조직 내에서 GitHub Actions의 제한 수준을 정의할 수 있다.
3. 엔터프라이즈 내에서 특정 작업만 사용하도록 설정하려면 엔터프라이즈 허용 및 엔터프라이즈가 아닌 작업 및 재사용 가능한 워크플로 선택을 활성화하고 사용 사례에 해당하는 옵션을 선택한다.

### 4.1.2 수동으로 Enterprise Server에 대한 공용 작업 동기화

GitHub에서 작성된 대부분의 공식 작업은 Enterprise Server와 함께 자동으로 제공되며, Marketplace에서 특정 시점에 캡처된다. 예를들어 `actions/checkou`, `actions/upload-artifact`, `actions/download-artifact`, `actions/labeler` 등 다양한 작업이 포함된다. 엔터프라이즈 인스턴스에 포함된 모든 공식 작업을 받고자 한다면 인스턴스의 작업 조직으로 이동한다.

[GitHub Actions 사용 정책 구성](#411-github-actions-사용-정책-구성) 바탕으로 Marketplace에서 사용할 수 있는 공용 작업에 자동으로 액세스하도록 Enterprise Server를 구성하고 해당 정책에 대한 사용 정책을 구성할 수 있다. 하지만 엔터프라이즈에서 사용할 수 있어야 하는 공용 작업을 보다 엄격하게 제어하려는 경우, `actions-sync` 도구를 사용하여 엔터프라이즈 인스턴스에 작업을 수동으로 다운로드하고 동기화 할 수 있다.


# 5. 조직 수준 [`GH-100`]

## 5.1 회사 표준 문서화

GitHub Actions 워크플로 만들기에는 여러 파일을 작성하고 워크플로 자체를 지정하는 여러 리포지토리를 만드는 작업이 포함되는 경우가 있기 때문에 생성에는 워크플로에서 사용할 작업, 컨테이너 또는 실행기도 포함된다. Enterprise Clouud 또는 Enterprise Server 인스턴스의 사용자 수에 따라, GitHub Actions 워크플로를 생성하기 위한 회사 표준이 없는 경우에는 작업이 쉽게 망가질 수 있다.

모범 사례로 조직 내 모든 사용자가 액세스할 수 있는 리포지토리의 Markdown 파일 또는 GitHub Wiki에 다음을 문서화하는 것을 권장한다.

* 스토리지에 대한 리포지토리
* 파일 혹은 폴더 명명 규칙
* 공유 구성 요소의 위치
* 지속적인 유지 관리 계획
* 기여 지침

### 5.1.1 워크플로 템플릿 생성

워크플로 템플릿은 엔터프라이즈에서 자동화를 다시 사용하고 유지 관리할 수 있는 좋은 방법이다. Enterprise Clouud와 Enterprise Server 모두에서 조직의 .github 리포지토리에 대한 쓰기 권한이 있는 사용자는 동일한 쓰기 액세스 권한이 있는 다른 조직의 구성원에게 사용할 수 있는 워크플로 템플릿을 만들 수 있다. 그런 다음 워크플로 템플릿을 사용하여 조직의 공용 및 개인 리포지토리에 새 워크플로를 생성할 수 있다.

**워크플로 템플릿 생성은 다음 두 단계로 수행한다.**
1. `.yml` 워크플로 파일을 생성한다.
2. 워크플로를 생성할 때 템플릿을 사용자에게 표시하는 방법을 설명하는 json 메타데이터 파일을 만든다.

> [!IMPORTANT]
> * **메타데이터 파일의 이름은 워크플로 파일과 동일해야 하며 `.yml` 확장명 대신 `.properties.json`을 추가해야 한다. 또한 두 파일은 모두 공용 .github 리포지토리 및 워크플로 템플릿이라는 디렉터리에 존재해야 하기 때문에 조직에 아직 이름이 존재하지 않은 경우 별도로 생성해야 할 수 있다.**  
> * **`5.1.1`의 예제 파일은 [Example-org-ci.yml](../github-crdential/example-sources/example-org-ci.yml)과 [Example-org-ci.json](../github-crdential/example-sources/example-org-ci.properties.json)에서 확인할 수 있다.**


| **매개 변수** | **설명** | **필수** |
| - | - | - |
| **이름** | 사용 가능한 템플릿 목록에 표시되는 워크플로 템플릿의 이름 | ✅ | 
| **설명** | 사용 가능한 템플릿 목록에 표시되는 워크플로 템플릿의 대한 설명 | ✅ |
| **iconName** | 템플릿 목록에서 워크플로 항목의 아이콘을 정의하고 동일한 이름의 SVG 아이콘이어야 하며 워크플로 템플릿 디렉터리에 저장해야 한다. | ❌ |
| **categories** | 워크플로의 언어 범주를 정의하고 사용자가 사용 가능한 템플릿을 볼 때, 동일한 언어로 된 템플릿이 더 명확하게 가능하다. | ❌ |
| **filePatterns** | 사용자 리포지토리의 루트 디렉터리에 정의된 정규식과 일치하는 파일이 있는 경우, 템플릿을 사용할 수 있도록 한다. | ❌ |

> [!TIP]
> **워크플로 템플릿이 생성되면 조직의 사용자는 Actions > New workflow > Workflows created by organization_name 아래에서 이를 찾을 수 있다.**

## 5.2 작업 및 워크플로에 재사용 가능한 템플릿

**워크플로 자동화**를 허용하며 효율적으로 관리하는 핵심 부분은 재사용 가능한 템플릿을 사용하는 것이 목표이다. 재사용 가능한 템플릿은 여러 리포지토리에서 개발을 표준화하고 간소화하여 중복성을 줄이고 유지 관리를 개선하는 데 도움이 된다.

GitHub Actions에서 재사용 가능한 템플릿은 여러 프로젝트에서 참조 및 사용할 수 있는 미리 정의된 작업 및 워크플로 를 참조하여 일관성을 보장하고 엔터프라이즈 수준 표준을 준수한다.

### 5.2.1 재사용 가능한 템플릿 유형

| **템플릿 유형** | **용도** | **예시** |
| - | - | - |
| **재사용 가능한 워크플로** | 리포지토리 간에 CI/CD 파이프라인을 표준화한다. | `ci-pipeline.yml`, `deploy-app.yml` |
| **재사용 가능한 작업** | 일반적인 자동화 논리를 캡슐화 한다. | `setup-env-action`, `security-scan-action` |
| **워크플로 템플릿** | 재사용 가능한 작업 구조를 정의한다. | `test-job.yml`, `build-job.yml` |

## 5.3 재사용 가능한 워크플로

재사용 가능한 워크플로는 여러 프로젝트에서 참조할 수 있는 별도의 리포지토리에 정의된 워크플로이다. 이를 통해 조직은 CI/CD 논리를 중앙 집중화 할 수 있다.

> [!NOTE]
> **`5.3 재사용 가능한 워크플로`의 예제는 각 [example-ci-pipeline](../github-crdential/example-sources/example-ci-pipeline.yml), [example-other-ci-pipeline](../github-crdential/example-sources/example-other-ci-pipeline.yml)에 작성되어 있다.**

## 5.4 재사용 가능한 작업

GitHub 작업은 특정 자동화 작업을 실행하는 모듈식 재사용 가능한 단위이다. 조직에서는 자주 사용하는 논리를 캡슐화하는 사용자 지정 작업을 만드는 경우가 많다.

#### 재사용 가능한 워크플로 사용의 이점

* 모든 리포지토리가 동일한 CI/CD 구조를 따르도록 한다.
* 중복성 및 유지 관리 오버헤드를 줄인다.
* 각 리포지토리를 수정하지 않고 중앙 집중식 업데이트를 허용한다.
* 리포지토리 전체에서 설치 논리의 중복을 줄인다.
* 워크플로 파일을 간소화하여 더 읽기 쉽고 파악하기 쉽게 만든다.
* 업데이트를 중앙 집중화 하여, 한 곳에서 수정 또는 개선 사항이 모든 워크플로에 반영된다.

# 6. 워크플로 템플릿 [`GH-100`]

워크플로 템플릿은 일반적인 작업에 미리 정의된 구조를 제공하여 조직 전체의 자동화를 표준화하는 데 도움이 된다. 이러한 템플릿은 재사용 가능한 워크플로의 광범위한 범주의 핵심 부분이다. 기업은 워크플로 템플릿을 활용하여 다음을 수행할 수 있다.

* 리포지토리 전체에서 모범 사례를 적용한다.
* 새 프로젝트에 대한 온보딩 및 설정을 가속화한다.
* CI/CD 프로세스에서 일관성을 유지한다.

# 7. 엔터프라이즈에서 작업의 액세스 및 사용 제어 [`GH-100`]

## 7.1 엔터프라이즈 내 작업에 대한 액세스 제어

GitHub Actions의 액세스 제어는 다음을 결정한다.
* 작업을 사용하는 워크플로를 실행할 수 있는 사람은 누구인지
* 조직 내에서 사용할 수 있는 작업이다.
* 자체 호스팅 실행기에서 워크플로를 안전하게 실행하는 방법
* 공유 GitHub Actions를 수정하고 업데이트할 수 있는 사용자이다.

> **엔터프라이즈 관리자는 개발자에게 유연성을 제공하고 자동화 워크플로에 대한 보안 및 거버넌스를 보장하는 것 사이의 균형을 유지해야 한다.**

### 7.1.1 작업 제어를 위한 조직 전체 정책

GitHub Enterprise를 사용하면 관리자가 조직 내의 모든 리포지토리에서 작업을 사용하는 방법을 제어하는 조직 전체 정책을 설정할 수 있다. 이러한 정책이 조직에서 타사 작업의 사용을 제한하고, 보안 조치를 적용해 자동화 워크플로를 표준화하는 데 도움이 된다.

### 7.1.2 작업에 대한 리포지토리 수준 권한

조직 전체 설정은 전역적으로 적용되지만 리포지토리 수준 권한은 워크플로를 실행하고 작업을 수정할 수 있는 사용자를 세밀하게 제어한다.

### 7.1.3 리포지토리 수준 워크플로 권한 관리

기본적으로 GitHub는 워크플로 권한을 `읽기`와 `쓰기`로 설정하지만 엔터프라이즈는 무단 수정을 방지하기 위해 명시적으로 요구하지 않는 한 워크플로 권한을 `읽기`로 제한 해야 한다.

## 7.2 조직 소유 작업을 수정할 수 있는 사용자 제한

조직에서 전용 리포지토리에서 재사용 가능한 GitHub Actions를 호스트하는 경우 권한이 부여된 사용자로 액세스가 제한되어야 한다.

* **분기 보호 규칙**을 사용하여 무단 수정을 방지한다.
* 작업이 업데이트되려면 **끌어오기 요청 승인**이 필요하다.
* **GitHub Teams & Role-Based RBAC(Access Control)**를 사용하여 쓰기 액세스를 제한한다.

### 7.2.1 외부 작업에 대한 액세스 제한

GitHub Actions를 사용하면 타사 작업을 사용할 수 있지만 외부 작업은 엄격한 검사를 진행하지 않으면 보안 리스크 발생 및 대응이 늦어져 위험을 초래할 수 있기 때문에 조직은 사용할 수 있는 외부 작업을 제어해야 한다.

#### 외부 작업 사용 위험

* **악성 코드 실행** : 신뢰할 수 없는 외부 작업으로 인해 취약성이 발생할 수 있다.
* **종속성 변조** : 타사 작업으로 인해 공급망 공격이 발생할 수 있다.
* **비밀 노출** : 외부 작업에서 실수로 비밀을 기록할 수 있다.
