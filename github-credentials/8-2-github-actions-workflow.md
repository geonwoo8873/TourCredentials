# 1. GitHub Actions에서 재사용 가능한 구성 요소 관리 및 활용 [`GH-100`]

GitHub Actions의 재사용 가능한 구성 요소는 여러 리포지토리에서 개발 및 자동화를 간소화하는 데 사용되는 워크플로, 작업 및 스크립트를 나타낸다. CI/CD 파이프라인을 표준화하고 유지 관리 가능성을 개선하며 중복 구성 작업을 줄이는 데 도움이 된다.

## 1.1 재사용 가능한 구성 요소 유형

1. 재사용 가능한 워크플로
   * 한 번 정의되고 여러 리포지토리에서 참조되었다.
   * 엔터프라이즈의 모든 프로젝트에 대한 표준 빌드 및 배포 워크플로의 특징을 가진다.
2. 사용자 지정 GitHub Actions
   * 반복되는 작업에 대해 생성된다.
   * 코드 린팅을 적용하기 위한 하나의 회사 전체 조직 단위의 작업이다.
3. 공유 스크립트
   * 작업을 자동화하기 위해 워크플로에 사용되는 Bash, PowerShell, Python와 같은 스크립트이다.
   * 코드 리포지토리에 대한 준수 보고서를 생성하는 반복적인 스크립트에 해당한다.

## 1.2 재사용 가능한 구성 요소에 대한 중앙 집중식 리포지토리 만들기

재사용 가능한 워크플로 및 작업을 위한 잘 구성된 리포지토리를 통해 쉽게 액세스하고 표준화할 수 있다.

| **리포지토리 유형**     | **용도**                                                            | **명명 규칙 예제**       |
| ----------------------- | ------------------------------------------------------------------- | ------------------------ |
| **액션 리포지토리**     | 여ㅕ러 프로젝트에서 사용되는 사용자 지정 GitHub Actions를 저장한다. | `org-actions-repo`       |
| **워크플로 리포지토리** | CI/CD 자동화를 위해 재사용 가능한 워크플로를 포함한다.              | `org-reusable-workflows` |
| **스트립트 리포지토리** | 자동화를 위해 재사용 가능한 스크립트를 유지 관리한다.               | `org-scripts-library`    |

### 1.2.1 파일 및 폴더에 대한 명명 규칙

유지 관리 효율성과 사용 편의성을 보장하려면 일관된 명명 규칙을 따라야한다.

#### 리포지토리 이름 지정

* 리포지토리에 설명적이고 일관된 이름을 사용한다.
  * `org-actions-repo`
  * `org-reusable-workflows`
  * `my-random-actions`
* 명확성을 위해 하이폰을 넣은 이름을 선호한다.
  * `ci-pipeline`
  * `CIPipeline`

#### 워크플로 및 작업 이름 지정

* 구조화된 형식을 따른다
  * `ci-test.yml`
  * `deploy-app.yml`
  * `build-container.yml`

#### 작업 이름 지정

* 작업 이름에는 PascalCase 또는 kebab-case를 사용한다.
  * `Run-Linter`
  * `run-linter`
  * `Runlinter`

# 2. 재사용 가능한 구성 요소의 지속적인 유지 관리 계획 [`GH-100`]

## 2.1 버전 관리 및 종속성 관리

* GitHub 릴리스(`v1.0.0`)를 사용한 `v2.0.0`이다.
* 워크플로에서 태그를 사용하지 `latest`않음으로써 예기치 않은 문제 발생을 방지한다.
* 의미 체계 버전 관리 사용:
  * 패치 업데이트 `v1.0.1` -> 버그, 사소한 업데이트를 수정한다.
  * 부 업데이트 `v1.1.0` -> 이전 버전과 호환되는 새로운 기능이다.
  * 주요 업데이트 `v2.0.0` -> 호환성이 손상되는 주요 업데이트 변경이다.

## 2.2 업데이트 및 유지 관리 자동화

* 병합하기 전에 워크플로 및 작업을 자동으로 테스트하는 GitHub 작업을 구현한다.
* Dependabot을 사용하여 재사용 가능한 작업에서 오래된 종속성을 검색한다.

## 2.3 사용 지침 문서화 및 제공

* 각 리포지토리에는 다음이 포함되어야 한다.
  * README.md
    * 구성 요소의 용도
    * 사용 방법
    * 워크플로 예제
  * CHANGELOG.md
  * CONTRIBUTING.md

## 2.4 보안 및 액세스 제어

* 작업 리포지토리에 대한 쓰기 액세스를 제한한다.
* 변경 내용을 관리하려면 코드 검토 및 GitHub CODEOWNERS 가 필요하다.
* GitHub 비밀 검사를 사용하여 워크플ㄹ로에서 비밀 하드 코딩을 방지한다.

## 2.5 모니터링 및 사용 중단 전략

* 피드백을 위해 GitHub 문제 및 토론을 설정한다.
* 사용 중단 계획
  * 이전 버전을 제거하기 전에 사용자에게 공지한다.
  * 주요 변경 내용에 대한 마이그레이션 가이드를 제공한다.

# 3. 기업에서 행동 지침을 분배하는 방법 [`GH-100`]

테스트, 배포 및 보안 검사와 같은 워크플로를 자동화할 수 있으며, 기업에서 작업을 효율적으로 배포하면 여러 팀이 동일한 워크플로를 재창조하는 대신 일반적인 자동화 작업을 다시 사용할 수 있다.

엔터프라이즈 내에서 GitHub Actions를 배포하는 세 가지 주요 방법이 존재한다.

1. GitHub Marketplace에서 게시 작업은 퍼블릭 배포용으로 사용된다.
2. Organization-Owned 리포지토리의 호스팅 작업은 내부 엔터프라이즈 배포용이다.
3. GitHub 패키지를 사용하여 컨테이너화된 작업을 보다 제어된 배포용으로 사용된다.

## 3.1 엔터프라이즈에서 작업을 배포하기 위한 모범 사례

| **모범 사례**     | **권장 사항**                                                                          |
| ----------------- | -------------------------------------------------------------------------------------- |
| **표준화**        | 명확한 설명서를 사용하여 재사용 가능한 작업을 위해 단일 리포지토리를 유지 관리한다.    |
| **버전 관리**     | 의미 체계 버전 관리를 사용하고 안정성을 위해 latest는 피한다.                          |
| **보안 검토**     | 작업을 게시하기 전에 코드 검토 및 자동화된 보안 검색이 필요하다.                       |
| **액세스 제어**   | 리포지토리 설정을 통해 내부 작업을 수정하고 사용할 수 있는 사용자를 제한한다.          |
| **정기 업데이트** | 변경 로그를 유지하고 주요 변경 내용을 방지하기 위해 업데이트에 대해 사용자에게 알린다. |

## 3.2 배포 방법 비교

올바른 방법을 선택하는 것은 비즈니스 요구 사항, 보안 요구 사항 및 확장성 고려 사항에 따라 달라지며, 기업은 GitHub Actions를 배포하는 구조적 접근 방식을 구현하여 DevOps 워크플로 전체에서 효율성, 보안 및 규정 준수를 보장해야 한다.

| **메서드**                        | **사용 사례**  | **액세스 제어**    | **보안 고려 사항**                                |
| --------------------------------- | -------------- | ------------------ | ------------------------------------------------- |
| **GitHub Marketplace**            | 공개 배포      | 제한 없음          | 공개적으로 액세스할 수 있으며 보안이 있어야 한다. |
| **Organization-Owned 리포지토리** | 내부 기업 사용 | 팀과 저장소의 역할 | 엄격한 권한 제어 필요                             |
| **GitHub Package**                | 내부 사용 보안 | 인증 필요          | 이미지는 변조로부터 보호되어야 한다.              |

# 4. 러너 관리 [`GH-100`]

## 4.1 워크로드에 적합한 러너를 선택한다.

GitHub 호스팅 실행기는 워크플로를 더 빠르게 간단하게 실행할 수 있는 방법을 제공하지만, 자체 호스팅 실행기는 사용자 지정 환경에서 워크플로를 실행할 수 있는 구성 가능한 방법이다. 예를 들어 조직의 IP 주소 허용 목록 또는 워크플로 실행을 위한 특수 하드웨어 구성을 사용해야 하는 경우, 자체 호스팅 실행길를 사용한다.

| **GitHub 호스팅 실행기**                                                                               | **자체 호스팅 실행기**                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 운영 체제, 사전 설치된 패키지 및 도구, 자체 호스팅 실행기 응용 프로그램에 대한 자동 업데이트를 받는다. | 자체 호스팅 실행기 응용 프로그램에 대해서만 자동 업데이트를 받으며, 운영 체제 및 기타 모든 소프트웨어를 업데이트할 책임이 있다.                        |
| GitHub는 관리 및 유지 관리된다.                                                                        | 이미 지불한 클라우드 서비스 또는 로컬 컴퓨터를 사용할 수 있으며, 또한 하드웨어, 운영 체제, 소프트웨어, 보안 요구 사항에 맞게 사용자 지정을 할 수 있다. |
| GitHub 요금제에서 무료 분을 사용하고, 무료 분을 초과한 후 분당 요금이 적용된다.                        | GitHub Actions와 함께 무료로 사용할 수 있지만, 실행기 머신을 유지 관리하는 비용은 사용자의 책임이다.                                                   |

## 4.2 엔터프라이즈의 실행기 관리

엔터프라이즈용 실행기를 관리하려면 GitHub 호스팅 및 자체 호스팅 실ㄹ행기를 구성하고 보호하여 효율적이고 안전한 CI/CD 워크플로를 보장한다. 이 관리에는 액세스를 제어하기 위한 IP 허용 목록 설정, 특정 IP 주소에 대한 실행기 액세스를 제한하여 보안 강화, 조직 정책 준수 보장 등이 포함된다. GitHub 호스팅 및 자체 호스팅 실행기 모두에 대한 IP 허용 목록의 적절한 구성은 내부 애플리케이션과 GitHub Actions 실행기 간에 안전하고 안정적인 상호 작용을 유지하는 데 매우 중요하다. IP 주소 범위의 변경 내용에 맞게 조정하고 최적의 보안을 유지하려면 이러한 구성에 대한 정기적인 업데이트 및 검토가 필요하다.

### 4.2.1 GitHub 호스팅 및 자체 호스팅 실행기에서 IP 허용 목록 구성

IP 허용 목록을 구성하면 실행기를 특정 IP 주소로 제한하여 실행기 액세스를 제어할 수 있다. 이 구성은 외부에서 무단 액세스 가능성을 방지하여 보안을 강화하지만 추가 네트워크 구성이 필요할 수 있다.

| **GitHub 호스팅 실행기**                                                                | **자체 호스팅 실행기**                                                                |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| GitHub 호스팅 실행기는 동적 IP 주소를 사용하므로 정확한 IP 허용 목록을 구성하기 어렵다. | 고정 또는 제어 IP를 사용하여 정확한 IP 허용 목록 또는 IP 기반 액세스 제어를 허용한다. |
| 조직은 GitHub의 게시된 IP 범위를 허용해야 한다.                                         | 보안을 강화하기 위해 방화벽 또는 VPN 뒤에 배치할 수 있다.                             |
| GitHub의 엔터프라이즈 보안 설정을 사용하여 GitHub 호스팅 실행기를 제한할 수 있다.       | 외부 서비스와 통신하려면 명시적 구성이 필요하므로 보안이 강화된다.                    |

### 4.2.2 허용된 IP 목록

허용된 IP 목록은 미리 정의된 주소에 따라 서비스 또는 리소스에 대한 액세스를 제한하는 보안 기능이다. 조직에서 IP 허용 목록을 구성할 때 다음을 수행할 수 있다.

* **보안 강화** : 신뢰할 수 있는 IP 주소만 허용하여 무단 액세스를 방지한다.
* **네트워크 트래픽 제어** : 인바운드 및 아웃바운드 요청을 알려진 IP 및 확인된 IP로 제한한다.
* **규정 준수 개선** : 권한 있는 네트워크에 대한 액세스를 제한하여 규정 준수를 보장한다.

| **GitHub 호스팅 실행기**                                            | **자체 호스팅 실행기**                                                  |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 조직은 주기적으로 변경되는 GitHub의 게시된 IP 범위를 허용해야 한다. | 관리자는 실행기 액세스가 허용되는 특정 IP 주소를 정의할 수 있다.        |
| GitHub 호스팅 실행기는 GitHub의 보안 설정을 통해 구성할 수 있다.    | 자체 호스팅 실행기는 방화벽, VPN 또는 클라우드 보안 그룹과 잘 작동한다. |

## 4.3 내부 애플리케이션이 GitHub-Hosted Runner와 상호 작용하도록 IP 허용 목록 구성

### 4.3.1 GitHub의 IP 주소 범위 이해

GitHub 호스팅 실행기는 특정 IP 주소 범위 내에서 작동한다. 내부 애플리케이션이 이러한 실행기와 통신할 수 있도록 하려면 방화벽을 통해 이러한 IP 범위를 허용해야 하며 작업 실행기의 IP 범위를 포함하여 GitHub 서비스에서 사용하는 모든 현재 IP 주소 범위를 나열하는 메타 API 엔트포인트를 제공한다. IP 범위가 변경 될 수 있으므로 이정보를 기반으로 허용 목록을 정기적으로 업데이트하는 것이 중요하다.

### 4.3.2 방화벽 구성

1. **GitHub의 IP 범위를 가져온다.**
   * 메타 API 엔드포인트를 사용하여 GitHub Actions 실행기에서 사용하는 최신 IP 주소 범위를 검색한다.
2. **방화벽 규칙 업데이트**
   * 방화벽에 규칙을 추가하여 이러한 IP 범위의 인바운드 및 아웃바운드 트래픽을 허용한다. 이 구성은 사용하고자 한다면 내부 시스템이 연결 문제 없이 GitHub 호스팅 실행기와 상호 작용할 수 있다.

### 4.3.3 자체 호스팅 실행기 사용을 고려한다.

IP 범위의 빈번한 변경으로 인해 GitHub 호스팅 실행기의 IP 허용 목록을 유지하는 것이 어려운 경우 네트워크 내에서 자체 호스팅 실행기를 설정하는 것이 좋다. 이 방법을 사용하면 실행기 환경 및 네트워크 구성을 광범위하게 제어할 수 있으나 자체 호스팅 러너를 사용하려면 높은 유지 관리와 엄격한 인프라 관리가 필요하다.

### 4.3.4 정기적으로 허용 목록 검토 및 업데이트

GitHub의 IP 주소 범위는 변경할 수 있으므로 방화벽의 IP 허용 목록을 주기적으로 검토가 필요하며 지속적인 업데이트 진행이 중요하다. 메타 API에서 IP 범위 검색을 스크립팅하여 이 프로세스를 자동화하면 수동 개입 없이 허용 목록이 최신 상태로 유지되도록 할 수 있다.

# 5. 퍼블릭 리포지토리에서 자체 호스팅 러너를 활성화하는 효과 및 잠재적인 악용 경로 [`GH-100`]

## 5.1 자체 호스팅 실행기 사용하도록 설정했을 때의 효과

1. **사용자 지정 및 성능 최적화**
   * 자체 호스팅 실행기는 하드웨어, 설치된 소프트웨어 및 환경 설정을 제어할 수 있다.
   * 워크플로는 전용 고성능 컴퓨터를 사용하여 성능에 최적화할 수 있다.
2. **비용 절감**
   * 무료 사용이 제한된 호스팅 실행기와 달리 자체 호스팅 실행기는 인프라에서 실행되어 비용 제약 조건을 줄인다.
3. **상태 지속성**
   * 자체 호스팅 러너는 GitHub 호스팅 러너처럼 작업 간에 초기화되지 않는다.
   * 종속성을 캐싱하고, 큰 데이터 세트를 다시 사용하고, 영구 상태를 유지 관리할 수 있다.
4. **보안 및 유지 관리 책임**
   * 보안 패치, 종속성 업데이트 및 시스템 모니터링은 실행기 소유자의 책임이 된다.
   * 잘못된 구성은 실행기를 외부 위협에 노출시킬 수 있다.

### 5.1.1 자체 호스팅 실행기의 잠재적인 남용 벡터

퍼블릭 리포지토리에서 자체 호스팅 실행기를 사용하도록 설정하면 상당한 보안 위험이 발생하기 때문에 누구나 끌어오기 요청을 제출하여 워크플로를 트리거할 수 있으므로 공격자는 다음과 같은 다양한 방법으로 이 기능을 악용할 수 있다.

1. 악의적인 행위자의 임의 RCE
   * 공격자는 자체 호스팅 실행기에서 자동으로 실행되는 악성 스크립트를 포함하는 끌어오기 요청을 제출할 수 있다.
   * 고급 권한이 있는 실행기인 경우, 공격자는 전체 시스템 액세스 권한을 얻게 된다.
2. 암호화 마이닝 및 리소스 악용
   * 공격자는 자체 호스팅 실행기를 악용하여 암호 화폐를 마이닝할 수 있으므로 예상치 못한 높은 CPU 및 GPU 사용량이 발생할 수 있다.
   * 운영 비용이 증가하고 합법적인 워크플로의 가용성이 줄어든다.
3. 데이터 반출 및 자격 증명 도난
   * 비밀(API 키, 데이터베이스 자격 증명, SSH 키)가 실행기에서 저장되면 공격자는 비밀을 추출할 수 있다.
   * 공격 벡터는 악의적인 끌어오기 요청이 저장된 환경 변수를 읽고 외부 서버로 보낼 수 있다.
4. Dos(서비스 거부) 공격
   * 공격자는 자체 호스팅 실행기를 오버로드하기 위해 다수의 끌어오기 요청으로 리포지토리를 가득 채울 수 있다.
   * 러너가 공유 인프라에 있다면, 다른 중요한 워크플로가 중단될 수 있다.
5. 수평 이동 및 네트워크 활용
   * 자체 호스팅 러너가 회사 네트워크 내에 있을 경우 공격자는 내부 시스템으로 침투할 수 있다.
   * 데이터 위반, 랜섬웨어 공격 또는 개인 리소스에 대한 지속적인 액세스로 이어질 수 있다.

#### 완화 전략

* 자체 호스팅 러너를 프라이빗 리포지토리에서만 사용할 수 있게 제한해야한다.
* 외부 참가자의 끌어오기 요청에 대한 워크플로 승인 필요
* 안전하고 격리된 환경에서 자체 호스팅 러너를 실행한다.
* 방화벽 및 네트워크 규칙을 사용하여 무단 액세스 차단한다.
* 중요한 비밀에 대한 액세스 제한 및 자격 증명 안전하게 저장한다.

# 6 워크로드를 지원하기 위한 적절한 실행기 선택 [`GH-100`]

## 6.1 GitHub 실행기 이해

GitHub Actions는 다음 두 가지 유형의 실행기를 지원한다.

1. **GitHub 호스팅 실행기**
   * GitHub에서 관리되며, 자동으로 프로비전되고 크기가 조정된다.
   * 일반 워크플로에 대해 미리 설치된 소프트웨어, 도구 및 종속성을 포함한다.
   * Windows, Linux 및 macOS를 사용할 수 있다.
   * 일반 자동화, 오픈 소스 프로젝트 및 빠른 설정에 권장된다.
2. **자체 호스팅 실행기**
   * 사용자가 관리하여 환경 및 리소스에 대한 모든 권한을 제공한다.
   * 사용자 지정 하드웨어, 온-프레미스 또는 클라우드 인프라에 대해 구성할 수 있다.
   * 캐싱 및 사용자 지정 종속성을 허용하는 작업 간의 영구 상태를 지원한다.
   * 프라이빗 리포지토리, 엔터프라이즈 워크로드 및 성능 집약적 작업에 권장한다.

## 6.2 GitHub에서 호스팅된 러너와 자체 호스팅된 러너 중에서 선택

GitHub Actions 워크플로를 실행할 수 있는 두 가지 유형의 실행기는 GitHub 호스팅 실행기와 자체 호스팅 실행기이다.

> [!IMPORTANT]
> **GitHub 호스팅 실행기는 Enterprise Cloud에만 사용할 수 있으며, Enterprise Server 인스턴스가 있는 경우 해당 섹션이 적용되지 않는다.**

GitHub 호스팅 실행기는 워크플로를 떠 빠르게 간단하게 실행할 수 있는 방법을 제공하지만 자체 호스팅 실행기는 사용자 지정 환경에서 워크플로를 실행할 수 있는 매우 구성 가능한 방법이다.

| **GitHub 호스팅 실행기**                                                                               | **자체 호스팅 실행기**                                                                                                         |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 운영 체제, 사전 설치된 패키지 및 도구, 자체 호스팅 실행기 응용 프로그램에 대한 자동 업데이트를 받는다. | 자체 호스팅 실행기 응용 프로그램에 대해서만 자동 업데이트를 받지만 운영 체제 및 기타 모든 소프트웨어를 업데이트할 책임이 있다. |
| GitHub는 관리 및 유지 관리된다.                                                                        | 이미 지불한 클라우드 서비스 또는 로컬 컴퓨터를 사용할 수 있으며, H/W, OS, S/W, Security에 맞게 사용자 지정할 수 있다.          |
| 모든 작업 실행에 대한 클린 인스턴스를 제공한다.                                                        | 모든 작업 실행에 대한 클린 인스턴스가 필요하지 않다.                                                                           |
| GitHub 요금제에서 무료 분을 사용하고, 무료 분을 초과한 후 분당 요금이 적용된다.                        | GitHub Actions와 함께 무료로 사용할 수 있지만, 실행기 머신을 유지 관리하는 비용은 사용자의 책임이다.                           |

## 6.3 러너 선택을 위한 운영 체제의 역할

1. **Linux**
   * 대부분의 워크프로드에 가장 적합하다.
   * 빠르고 비용 효율적이며 널리 지원된다.
   * CI/CD, 스크립팅, Docker 및 자동화에 사용된다.
2. **Windows**
   * .NET, Windows 기반 소프트웨어 및 GUI 앱에 필요하다.
   * PowerShell, Windows 관련 종속성 지원한다.
3. **macOS**
   * macOS 실행기는 IOS, macOS, Xcode 및 Apple 관련 빌드에 필요하다.
   * Swift, Objective-C 및 macOS 애플리케이션 지원한다.

#### 실행기 선택을 위한 모범 사례

* GitHub 호스팅 실행기를 일반적인 워크플로 및 자동화를 위해 사용한다.
* 사용자 지정 환경, 대규모 워크로드 또는 보안에 민감한 애플리케이션자체 호스팅 실ㄹ행기를 사용한다.
* 성능 및 비용 효율성으로 인해 대부분의 워크로드에 대해 Linux 실행기를 선택한다.
* 호환성을 위해 필요한 경우에만 Windows 또는 macOS 실행기를 사용한다.
* 보안 위험을 방지하기 위해 자체 호스팅 실행기를 정기저긍로 업데이트하고 모니터링한다.

## 6.4 GitHub 호스트된 및 자체 호스팅 실행기 비교

GitHub Actions는 워크플로를 실행하기 위한 두 가지 유형의 실행기를 지원한다.

1. **GitHub 호스팅 실행기** : GitHub에서 관리되고, 자동으로 프로비전이 되어, 공통 개발 도구로 미리 구성된다.
2. **자체 호스팅 실행기** : 사용자가 관리하므로 환경, 리소스 및 구성을 완벽하게 제어할 수 있다.

## 6.5 주요 차이점 및 고려 사항

1. **설정 및 유지 관리**
   * GitHub 호스팅 실행기는 설정이 필요하며, 사용자는 워크플로 실행을 즉시 시작할 수 있다.
   * 자체 호스팅 실행기는 수동 설치, 구성, 업데이트 및 보안 관리가 필요하다.
2. **보안 위험**
   * GitHub 호스팅 실행기는 각 작업 후에 다시 설정 되는 격리된 가상 머신에서 실행 되어 공격 표면을 최소화한다.
   * 자체 호스팅 실행기는 작업 간에 유지되므로 손상된 실행기는 여러 워크플로 실행에서 악용될 수 있다.
3. **성능 및 비용 고려 사항**
   * GitHub 호스팅 실행기는 표준 환경을 제공하면서 사용량 제한이 있다.
   * 자체 호스팅 실행기는 더 나은 성능 튜닝을 허용하지만 인프라 및 유지 관리 비용이 필요하다.
4. **네트워킹 및 액세스**
   * GitHub에서 호스팅되는 러너는 추가 구성이 없으면 프라이빗/내부 리소스에 액세스할 수 없다.
   * 자체 호스팅 실행기는 내부 시스템에 액세스할 수 있으므로 프라이빗 리포지토리, 내부 도구 및 온-프레미스 배포에 적합하다.
